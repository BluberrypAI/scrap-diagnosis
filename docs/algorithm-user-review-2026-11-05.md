# 문진 알고리즘 사용자 관점 평가와 SCRAP UI 개선안

기준일: 2026-11-05 · 규칙 DB: `rules-b154c705c0eb`

## 평가 결론과 범위

현 구조는 근거를 추적할 수 있는 규칙 기반 계산기로서 유지할 가치가 있다. 그러나 질문 수 최적화, 후속 분류에 필요한 정보의 완결성, 답변 수정, 모름 처리, 저장·결과 안내가 사용자 업무 흐름으로 연결되지 않았다. 우선순위는 **잘못된 구체화 방지 → 막히는 흐름 복구 → 질문 부담 감소 → 설명 개선**이다.

이번 작업은 평가와 개선안 제시다. 제품의 알고리즘, 규칙, `SCRAP.html`, `survey.js`, `survey.css` 동작은 변경하지 않았다. 합성 입력 감사 스크립트와 결과를 추가했다. 실제 고객 데이터나 비밀정보는 사용하지 않았다.

확인 근거:

- 소스: `engine.py`, `candidates.py`, `annex4.py`, `compact.py`, `recycling.py`, `web/app.py`, `web/scrap/survey.js`, `facts.yaml`, `rules.yaml`, `s4_map.yaml`, `rules_s3.yaml`.
- 실행: `python tools/audit_user_flow.py`. 출력: `audit/user_flow_audit_2026-11-05.json`.
- 실제 브라우저: 문진 시작, 첫 질문과 선택 후 후보 안내, 나가기 동작을 확인했다. 원본 HTML의 브라우저 직접 열기는 file URL 정책에 차단되어 시각 비교를 수행하지 못했다. 원본 파일은 소스로 읽었다.
- 이 평가는 코드 내부의 일관성과 사용자 흐름을 다룬다. 현행 법령 전체의 정확성, 법률적 유효성, 실제 사용자 이해도는 별도 검증 대상이다.

## 1. 후보 수가 안 줄어드는 질문을 모두 불필요하다고 볼 수는 없다

현재 단계는 S0 폐기물 여부, S1 적용 법률, S2 사업장 여부, S3 지정 여부, S4 분류번호, S5 재활용 유형이다. 앞의 세 단계는 코드 후보를 줄이는 것 외에 대상 여부와 적용 범위를 결정한다.

처음부터 모든 답을 직접 입력한 합성 경로:

| 상황 | 엔진 질문 수 | 최종 제시 상태 | 해석 |
|---|---:|---|---|
| 잔류물·기름·PCB·유해화학물질 관련 없음, 배출시설 있는 사업장의 금속 | 11 | 고철 `51-29-01`, 잠정 결과 | 첫 4개 답 후에도 후보 272개 |
| 위 사업장의 고체 합성수지 | 11 | `51-03-01`, 잠정 결과 | 종류·상태·위험 확인을 거쳐 세부 번호 직접 선택 |
| 소규모 금속 배출, 사업장 해당 경로 모두 부정 | 14 | 생활폐기물 쪽 잠정 결과 | S2 중 S3 질문을 먼저 수행한 뒤 S2로 돌아옴 |
| 폐유 | 6 | `06-01-01`, 재활용 유형, 잠정 결과 | 짧지만 PCB 관련 확인을 건너뜀 |
| 액체 폐산 pH 1 | 11 | `02-01-02`, 잠정 결과 | 중간에 묻는 다른 오염 조건 일부는 최종 pH 입력 후 없어도 같은 경로 결과 |

질문 수는 엔진이 요청하는 사실 항목 수다. 화면의 그룹 선택 클릭, 첫 설명 입력, 재확인, 실제 서류 확인 시간은 포함하지 않는다. 이 다섯 합성 사례는 사용자 집단의 평균이나 목표 질문 수를 뜻하지 않는다.

금속 사례의 첫 질문 `material_fate`와 배출시설 질문은 모든 선택지의 **현재 코드 후보 집합**이 같다. 그렇지만 후속 답과 결합하면 폐기물 해당 여부나 S2 경로가 달라진다. 따라서 현재 후보 수만으로 삭제하면 안 된다.

**실제 화면 문제:** 첫 질문의 ‘내보낸다’를 선택하자 `272개 후보를 272개로 줄이는 답이에요.`가 표시된다. `survey.js`의 선택 후 안내는 감소량이 0인지 확인하지 않는다. 반대로 0개가 되는 선택은 범위 밖·적용 제외일 수 있어 ‘후보를 많이 줄이는 좋은 답’처럼 표현해서도 안 된다.

개선: 질문 목적을 `적용 범위 확인`, `위험 확인`, `코드 구분`, `자료 확인`으로 구분한다. 앞 단계 우측 패널에는 ‘폐기물 여부와 적용 대상을 확인 중입니다’를 표시하고, 분류 단계에서만 후보 수와 제외 이유를 중심으로 보여 준다.

## 2. 우선 수정할 문제

### P1 — 지정 여부가 정해지면 후속 결론에 필요한 확인까지 끝난 것으로 취급

재현:

1. 공통 입력: 외부로 내보냄, 순환자원 인정 없음, 다른 법 대상 아님, 배출시설 있음.
2. 종류 `waste_oil` 선택 → PCB 확인 없이 S4로 이동한다.
3. `06-01-01` 선택 → S5 `ALLOWED_TYPES`가 제시된다.
4. 같은 조건에서 `pcb_possible=UNKNOWN`을 명시해도 같은 구체적 결과가 제시된다.
5. 여기에 액체, `pcb_possible=true`, `pcb_mg_l=3`을 주고 PCB 번호 `08-01-00`을 선택하면 S5는 `PROHIBITED`가 된다.

이는 법령을 새로 해석한 결론이 아니라, **현재 저장소 자체의 PCB 규칙과 제외 대응표에 비춘 불일치**다. `engine.py`는 하나의 단계 결론이 참이면 다음 단계로 진행한다. `annex4.py`는 이미 성립한 지정 사유로만 코드 범위를 만들기 때문에 아직 확인하지 않은 다른 사유를 놓칠 수 있다.

strict 모드에서는 두 결과 모두 사람 검토 전이라는 이유로 잠정 표시된다. 이 표시는 유지해야 하지만, 미확인 사실에 따라 분류번호·재활용 금지가 바뀔 수 있다는 구체적인 이유는 별도로 표현해야 한다.

개선: ‘지정폐기물에 해당함’과 ‘분류번호 및 재활용 조건까지 결정할 정보가 충분함’을 분리한다. 후속 코드 범위나 금지·제한 조건을 바꿀 수 있는 미확인 조건은 필수로 남긴다. 해당 정보가 모름이면 지정 여부만 제시하고 코드·유형은 보류한다.

### P1 — 앞 답을 바꿔도 뒤 답이 유효한지 다시 확인하지 않음

재현: 고체 합성수지와 `code=51-03-01` 입력을 완료한 후 API 처리 함수에서 종류만 `synthetic_rubber`로 변경한다. 기존 코드가 그대로 남고 S4·S5까지 제시된다. `51-03`이라는 같은 범위를 공유하므로 범위 검사만으로 잡지 못한다.

`web/app.py`의 답변 변경은 전달받은 키 하나만 덮어쓴다. SCRAP 화면에서는 답 목록에 개별 수정 기능이 없으며, 이전 버튼으로 여러 번 되돌아가야 한다.

개선: 답변의 의존 관계를 기록한다. 종류·발생 공정·오염 여부를 바꾸면 영향받는 코드 선택, ‘그 밖의’ 확인, 분석자료와 결과를 ‘재확인 필요’로 바꾼다. 그대로 유효한 답은 보존하고 영향받은 항목만 확인받는다. 같은 범위 안에서도 종류와 세부 코드가 모순되는지 검사한다.

### P1 — S4에서 ‘모름’을 답해도 같은 질문이 반복됨

재현: 합성수지 분류 단계에서 `code=UNKNOWN`을 주면 다음 질문은 다시 `code`다. 같은 상태를 세 번 평가해도 반복된다. ‘그 밖의’ 확인 항목인 `no_specific_code_applies=UNKNOWN`도 같은 질문으로 돌아간다.

원인: S4는 UNKNOWN 상태에서도 `_open()`으로 동일 질문을 내보낸다. 화면은 다음 질문이 있으면 계속 질문 화면을 보여 주므로 확인 안내로 이동하지 않는다.

개선: ‘모름’을 정상적인 상태로 처리한다. 기존 서류 확인, 물질·공정의 차이 설명, 분석 필요, 기관 확인 중 해당 경로를 제시하고 중단·재개할 수 있게 한다. 사용자가 새 정보 없이 같은 답을 반복하도록 만들지 않는다.

### P1 — ‘자동 저장됨’과 업무 데이터 저장·재개가 연결되지 않음

`survey.js`는 시작 화면에서도 ‘자동 저장됨’을 표시한다. 답은 서버의 메모리 `SESSIONS`에 보관되고, 브라우저는 세션 ID를 재개 가능한 저장소에 기록하지 않는다. 새로고침 시 문진을 복구하는 코드가 없다. 결과의 ‘저장하고 처리 경로 선택’은 링크 이동이며 결과 저장 API를 호출하지 않는다. README도 문진 외 화면은 디자인 데모임을 명시한다.

개선: 폐기물 ID·세션 ID·현재 답·규칙 버전·기준일을 연결해 저장하고 저장 성공 후 표시한다. 상세 화면과 경로 선택 화면은 저장된 결과를 읽어야 한다. 그 연결 전에는 현재 저장 범위를 정확하게 안내해야 한다.

## 4. 제안하는 질문 선택 방식

대안은 세 가지다.

1. **문구·순서만 정리:** 작게 바꿀 수 있지만 조기 확정, 답 수정, 모름 반복은 별도 수정해야 한다.
2. **기존 규칙 엔진을 유지하고 문진 선택·상태 관리를 보강 — 권고:** 법적 판정 규칙과 사용자 질문 선택을 분리한다. 근거 추적을 유지하면서 사용자 문제를 해결할 수 있다.
3. **LLM이 질문과 분류를 주도:** 새 검증 부담이 크다. 현재 문제를 해결할 우선 수단으로 권하지 않는다. 사실 추출·용어 설명 역할은 유지 가능하다.

권고안의 원칙:

- 질문별로 필요한 이유, 영향을 주는 결론, 대상 사용자, 자료 출처, 답변 부담, 재확인 조건을 기록한다.
- 안전·법 적용·금지 조건에 필요한 확인을 먼저 보장한다. 단순 후보 감소량이 큰 질문이 이를 밀어내지 못하게 한다.
- 그 외에는 실제 남은 분기들을 얼마나 구분하는지와 응답 부담으로 순서를 정한다. 사용자별 답 분포가 없으므로 ‘평균 정보이득이 최적’이라는 주장은 하지 않는다. 초기에는 최악의 경우에 남는 분기 수와 확인 비용을 이용한 규칙을 제안하고 비교 평가한다.
- 질문을 삭제하려면 현재의 즉시 후보 수뿐 아니라 다른 미확인 답과의 결합까지 확인한다. 미확인 답의 가능한 값에 따라 최종 분류·금지 조건이 달라지면 질문을 남긴다.
- 사업장 공통 정보는 근거 서류·확인일과 함께 재사용한다. 폐기물마다 다른 종류·오염·성상은 재사용 범위를 제한한다.
- 질문을 합쳐 화면 수를 줄여도 각각의 사실과 모름 상태는 보존한다. 언급되지 않은 위험을 자동으로 ‘없음’ 처리하지 않는다.

이는 구현 전 제안이며 질문 수 감소나 정확도 향상은 아직 측정하지 않았다. 질문의 목적과 적용 대상을 명시하고 관련된 질문만 분기하는 방향은 [GOV.UK 문진 구조 지침](https://www.gov.uk/service-manual/design/form-structure)과도 부합한다.

## 5. SCRAP.html을 기준으로 한 화면 적용

`SCRAP.html`의 전체 디자인을 기준으로 삼는다. 현재 주입 방식과 `survey.js`·`survey.css`를 재사용하는 방향을 우선 검토하고, 새 디자인 체계나 전면 재구성은 도입하지 않는다.

| 기존 영역 | 유지할 시각 구조 | 개선할 내용 |
|---|---|---|
| `L3-WorkBar` | 나가기·물질명·저장 상태 | 실제 저장 성공, 저장 실패, 다시 이어 하기 표시 |
| 질문 카드 | 제목·도움말·선택 카드·이전/다음 | 일상 용어로 질문, 확인 서류 안내, 모름 선택 후 별도 행동 제공 |
| `CandidatePanel` | 우측 보조 패널 | 앞 단계는 적용·위험 확인 상황, 분류 단계는 후보와 제외 이유 표시. 272→272 감소 안내 제거 |
| 입력 답변 목록 | 접어 보는 답 목록 | 개별 수정, 영향받은 뒤 답의 재확인 상태 표시 |
| 베리 | 기존 캐릭터·말풍선 | 질문의 구체적 목적, 막혔을 때 다음 행동 설명 |
| 근거 오버레이 | 기존 근거 패널 | 판정에 사용한 값·조건·법령 판과 직접 출처 연결 |
| 결과 카드 | 배지·분류번호·재활용 그룹 | 사용자 선택 코드, 잠정 사유, 미확인 위험, 표 조회와 실제 실행 준비 상태 구분 |

다단계 양식에서 논리적 단계와 진행 상태를 이해하기 쉽게 전달하는 원칙은 [W3C WAI 다단계 양식 지침](https://www.w3.org/WAI/tutorials/forms/multi-page/)을 참고한다. 현재 화면의 접근성 적합성을 검증했다는 뜻은 아니다.

## 6. 개선 완료를 판단할 조건

1. 폐유·PCB 예시에서 PCB 미확인 상태로 구체적 코드와 재활용 가능 결과를 확정하지 않는다. 필요한 확인 또는 명시적 보류를 제시한다.
2. S4 ‘모름’ 후 동일 질문을 무한 반복하지 않고, 확인 방법과 재개 경로가 나온다.
3. 종류를 합성수지→합성고무로 바꾸면 기존 코드에 대해 재선택 또는 근거 있는 일관성 검사가 수행된다.
4. 새로고침·나가기 후 돌아오기·서버 재시작 각각의 저장·복구 조건을 정의하고 실제 결과로 확인한다.
5. 각 질문에 영향을 주는 판단과 확인 자료가 설명된다. 후보 수가 같은 경우 감소했다고 말하지 않는다.
6. 기존 판정 비교 외에 문진 처음부터 끝까지의 흐름, 잘못 이해한 선택, 수정, 모름, 혼합 상황을 검증한다.
7. 같은 사례·조건으로 개선 전후 질문 수, 실제 확인 시간, 모름 반복, 복구 성공, 위험 확인 누락, 잘못된 구체적 결론을 비교한다. 실사용자 관찰로 이해도를 별도로 확인한다.

전체 기본 테스트 실행은 HTTP `TestClient`에서 멈췄다. 단일 검사 재현의 스택은 Windows asyncio 이벤트 루프의 `socketpair()` 내부 `accept()` 대기를 가리켰다. 해당 전송 검사를 격리 제한 밖에서 다시 실행해 8개 모두 통과했다. 원래 실행은 중단했으며 제품 수정으로 해결했다고 보고하지 않는다. 두 완료 실행을 합하면 **566 passed, 4 skipped**다.

현재 EVAL 재채점은 단계 기대값 89개 중 CORRECT 8, CORRECT_STOP 28, STOPPED 41, NOT_COMPARABLE 9, OVERCONFIDENT 1, WRONG 1이다. 실제 사용자 문진 완료율이나 서비스 정확도가 아니다.

특히 `tools/evaluate_cases.py`는 S0~S3를 단계별로 직접 평가하고 S4는 범위 포함 여부를 보며, S5는 제품의 `evaluate_s5()` 대신 별도 단순 조회 함수로 채점한다. 기관 R코드가 결과에 모두 포함되면 맞음으로 보므로 과다 허용도 충분히 평가하지 않는다. 기존 평가기의 WRONG·OVERCONFIDENT를 그대로 현재 제품의 법적 오류로 확정할 수 없고, 오래된 사례의 법령 시점 차이도 검토해야 한다. 이 평가 체계만으로 문진 알고리즘이 충분히 검증되었다고 보기 어렵다.
