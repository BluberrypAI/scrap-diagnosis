# 동기 vs 비동기 서버 부하 테스트 (진단 엔진)

작성 기준: main `fdddf77`, Windows, 단일 uvicorn 워커(1 프로세스), 8코어 노트북. 실제 LLM/Azure/PostgreSQL 없이 한 턴을 모사한 결과다.

## 요약

- 한 턴의 지연(요청 1건)은 동기/비동기가 같다. 차이는 **동시에 진행 중인 턴이 많을 때**만 난다.
- 동기 서버의 기본 스레드 40개가 한도다. 동시 턴이 40을 넘으면 줄을 선다(L=3s, N=200: 총 15.3s, p95 15.3s). 스레드 수를 200으로 올리면 비동기와 거의 같아진다(총 4.3s vs 4.4s).
- 이 서비스의 실제 병목은 서버 모델보다 **Azure OpenAI 쿼터(TPM/RPM)** 일 가능성이 크다(아래 계산, 추정).
- 비동기로 가려면 규칙 엔진(CPU)을 반드시 스레드로 내보내야 한다. 다만 이 부하에서는 인라인 실행의 손해가 측정상 크지 않았다(아래).

## 방법

`scripts/loadtest.py`가 앱 2종을 프로세스 안에서 만들고 uvicorn으로 띄운다(포트 자동, 종료도 스크립트가 처리). 각 요청은 한 턴을 모사한다.

| 단계 | 구현 |
|---|---|
| DB 읽기/쓰기 | 3ms 대기 x2 (`time.sleep` / `asyncio.sleep`) — **모사**. aiosqlite가 설치돼 있지 않아 의존성을 추가하지 않았고, 실제 DB I/O는 측정하지 않았다 |
| 규칙 엔진 | 실제 `run_engine`, 실제 KB(`data/real`), 대표 사실 집합(소재 PP 등 9개 사실 확정) |
| LLM | `sleep(L)`, L = 3s (1s는 N=200만) |

모드 4종: `sync`(sync def, 스레드풀 40), `sync200`(같은 코드, anyio CapacityLimiter 200), `async`(CPU는 `anyio.to_thread.run_sync`), `async_inline`(CPU를 이벤트 루프에서 직접 실행). 클라이언트는 `httpx.AsyncClient`로 N개를 동시에 쏜다(N = 20/50/100/200).

측정한 엔진 CPU: 대표 사실 집합 평균 **4.3ms/턴**, 빈 세션 첫 질문은 **약 0.2~0.3s/턴**(`--heavy`).

## 해석

1. **단일 턴 지연은 같다.** N=20에서는 네 모드 모두 총 약 3.1s로 L과 같다.
2. **동기의 한계는 스레드 수다.** 동기 서버는 LLM 대기 동안 스레드 1개를 붙들고 있어서, 동시 진행 턴 > 40이면 대기열이 생긴다(처리량 상한 ≈ 40/L). N=50부터 p95가 L의 2배로 뛴다. 스레드풀을 200으로 올리면 이 구간이 사라지고 비동기와 구분되지 않는다. 즉 이 부하(I/O 대기 위주)에서 async의 이득은 "스레드 노브로 대체 가능한" 수준이었다.
3. **비동기가 더 이기는 곳(이번 테스트에서는 측정하지 않음).** 동시 연결이 수천 단위일 때(스레드당 메모리/컨텍스트 스위칭), SSE/스트리밍 응답 유지, 한 턴 안에서 여러 호출을 병렬로 fan-out할 때(예: 서류 여러 건 동시 추출).
4. **CPU는 비동기에서도 병목이다.** 엔진은 순수 파이썬이라 GIL 때문에 스레드로 내보내도 병렬이 안 된다. 빈 세션처럼 CPU가 무거우면 모드와 무관하게 처리량이 약 3~4턴/s로 수렴했다(`--heavy`). 스레드를 늘려도(sync200) 나아지지 않았다(오히려 N=100에서 낮게 나왔으나 1회 측정이라 노이즈일 수 있다). 그러니 CPU 병목은 async/sync 선택이 아니라 **워커 프로세스 수**로 풀어야 한다.
5. **인라인 함정.** 대표 사실 집합(4ms)에서는 인라인 실행이 오히려 가장 빨라 보일 만큼 손해가 안 보였다. 하지만 무거운 턴(0.2s+)에서는 이벤트 루프가 그동안 멈춰 다른 모든 요청(헬스체크 포함)이 같이 지연되고 처리량이 가장 낮았다(N=50: 2.75턴/s vs 약 3.6, N=100: 2.65 vs 약 2.9~4.0 — 차이가 크지 않고 노이즈 범위일 수 있다). 이 테스트는 "루프가 멈춘다"를 직접 재지는 않았다(헬스체크 지연 미측정). 엔진 호출은 항상 `to_thread`로 감싼다.
6. **쿼터 병목(추정).** 아래 표.

## Azure OpenAI 쿼터 병목 (추정치)

실측: 대표 턴의 extractor 사용자 프롬프트 11,301자 + 시스템 프롬프트 1,717자 = 13,018자. 가정: 한글 JSON은 **토큰 ≈ 글자수/2** → 입력 약 **6,500 토큰**. 출력은 **300 토큰으로 가정**(미측정). 한 턴 LLM 호출 1~2회(실측 호출당 1.1~3.3s). 따라서 턴당 약 6.8k(1회) ~ 13.6k(2회) 토큰. 쿼터 값은 가정이다(실제 배포 쿼터로 바꿔 계산할 것).

| 가정한 TPM | 턴/분 (호출 1회) | 턴/분 (호출 2회) |
|---|---|---|
| 100k | 약 14 | 약 7 |
| 500k | 약 73 | 약 37 |
| 1M | 약 147 | 약 73 |

비교: 동기 기본(스레드 40, L=3s)의 이론 상한은 약 13턴/s = 780턴/분. TPM 1M이어도 쿼터 상한(최대 약 2.5턴/s)이 스레드풀 상한보다 훨씬 낮다. 즉 쿼터가 이 정도 이하라면 **서버 모델을 바꿔도 처리량은 쿼터가 정한다.** 쿼터를 넘으면 429가 나므로 재시도/큐잉/동시성 제한(세마포어)이 먼저 필요하다. 프롬프트가 큰 것(사실 목록 catalog_view)이 토큰 대부분이므로 프롬프트 축소·캐싱이 쿼터 면에서 가장 효과가 클 수 있다.

## 권고

- **동시에 진행 중인 LLM 대기 턴이 약 40 이하**(스레드 기본값 이내)이면 지금의 동기 구조로 충분하다. 약 **40~200**이면 동기 유지 + anyio 스레드풀 상향(`total_tokens=200`)으로 충분했다(측정: async와 총 시간 차이 5% 이내). 그 이상(수백~수천 동시 연결), 스트리밍, 병렬 fan-out이 생기면 그때 async 전환을 검토한다.
- 동시 턴 수 추정: (분당 턴 수 / 60) x 턴 지연(초). 예) 분당 300턴 x 6초 = 약 30 동시 턴.
- 이번 측정에 **포함되지 않은 것**: 동기 SQLAlchemy의 DB 커넥션 풀(기본 5+오버플로 10 = 15). 세션을 LLM 호출 동안 잡고 있으면 스레드보다 먼저 풀이 한도가 된다. 전환 전에 확인할 것. 또 asyncpg/aiosqlite 실제 I/O는 측정하지 않았다.
- async 전환 시 필수: `run_engine`과 모든 sync 라이브러리 호출은 `to_thread`로. CPU가 병목이면 uvicorn `--workers`(프로세스) 증가.
- 먼저 할 일: 실제 Azure 쿼터(TPM/RPM) 확인 -> 위 표로 상한 계산 -> 429 대응(재시도/세마포어).

## 다시 돌리기

```
uv sync
PYTHONIOENCODING=utf-8 uv run python scripts/loadtest.py            # 전체 (약 3분)
PYTHONIOENCODING=utf-8 uv run python scripts/loadtest.py --quick    # N=20,50만
PYTHONIOENCODING=utf-8 uv run python scripts/loadtest.py --heavy    # CPU 무거운 턴 (수 분)
```

결과는 마크다운 표로 출력된다. 서버는 스크립트가 띄우고 끝나면 정리한다. 수치는 머신/부하에 따라 달라지므로 같은 환경에서 비교할 것.
