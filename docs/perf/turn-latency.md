# 문진 한 턴의 지연 (실제 Azure, 2026-11-09)

서버(scrap-server) → 엔진 호출의 타임아웃을 정하기 위한 측정이다.

- 스크립트: `uv run python scripts/turn_latency.py --runs 3 --db postgresql+psycopg://wd:wd@localhost:55432/waste_diagnosis`
- 환경: Windows 노트북, 엔진 1 프로세스, PostgreSQL 17(docker compose), Azure AI Foundry 배포(추론 모델), 요청 1개씩(동시 부하 없음)
- 시나리오: PP 문진 자유 입력 3턴 + 버튼 1턴, 3회 반복

## 결과

| 턴 | 1회(s) | 2회(s) | 3회(s) | AI 호출 |
|---|---|---|---|---|
| 건 생성 + 첫 메모 | 7.42 | 4.09 | 4.70 | 추출 + 응답 |
| 자유 입력 1 | 4.09 | 4.01 | 5.21 | 추출 + 응답 |
| 자유 입력 2 | 5.10 | 8.16 | 5.80 | 추출 + 응답 |
| 버튼 | 1.35 | 2.15 | 1.54 | 응답만 |

턴 12개: **중앙값 4.40s, p95 7.42s, 최대 8.16s**. AI 호출 하나는 1.2~5.9s였다. 엔진 자체(규칙 평가·DB)는 턴당 수십 ms 이하라 시간 대부분이 AI 대기다.

## 서버 타임아웃 제안

- 기존 분류 호출의 12초는 정상 턴(최대 8.2s)은 넘기지만 여유가 작다. AI가 느린 시간대에는 넘을 수 있다.
- **제안: 새 엔진 경로는 30초.** 넘으면 서버는 "응답이 늦어요, 다시 보내 주세요"로 안내하고, 같은 요청을 다시 보내기 전에 `GET /cases/{id}`로 그 턴이 저장됐는지 확인한다(엔진은 턴을 끝까지 처리하고 저장한다).
- 엔진 쪽 상한: AI 호출 하나는 `LLM_TIMEOUT_SECONDS`(기본 60초)와 재시도 2번을 쓴다. 최악의 경우가 서버 타임아웃보다 길 수 있다. 운영에서는 `LLM_TIMEOUT_SECONDS=12` 정도로 낮추는 것을 권한다. AI 호출이 실패하면 엔진은 버튼 답변용 기본 문장(템플릿)으로 턴을 끝낸다.

## 측정하지 않은 것

동시 요청이 많을 때의 지연은 [sync-vs-async.md](sync-vs-async.md)(모의 AI 지연)를 본다. 실제 Azure 쿼터(분당 요청·토큰 수) 한도에서의 지연은 재지 않았다.
