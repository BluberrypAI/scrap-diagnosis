# 문진 한 턴의 지연 (실제 Azure, 2026-11-09)

서버(scrap-server) → 엔진 호출의 타임아웃을 정하기 위한 측정이다.

## 2026-11-17 통합 재검사에서 바꾼 설정

동시 문진 시험에서 새 건 생성 한 건이 server의 30초 대기를 넘어 `ReadTimeout` → 503으로 끝났다. 아래 11월 9일의 30초 제안은 이 구성의 현재 권장값이 아니다.

- **재시도는 한 곳에서 관리한다.** SDK 자동 재시도 2번을 없앴다(`max_retries=0`). 추출기·응답기의 기존 최대 1회 재시도와 guard·템플릿 대체는 유지한다. 실패한 호출도 기존 Trace에 남는다.
- 한 턴의 추출/응답은 각 최대 2번, 기본 호출 대기 60초 기준 모델 대기 예산은 240초다. 이전에는 SDK 재시도까지 겹쳐 호출 횟수가 3배까지 늘 수 있었다.
- 통합 infra에서 `DIAGNOSIS_LLM_TIMEOUT_SECONDS=60`, `DIAGNOSIS_ENGINE_TIMEOUT_SECONDS=300`을 연결했다. 후자는 규칙·DB 처리 여유를 포함한 서버의 HTTP 대기 설정이다. 웹 nginx 대기 600초보다 짧다. 300초가 실제 평균 응답시간이라는 뜻은 아니다.
- `LLM_TIMEOUT_SECONDS`를 바꾸면 서버 대기도 함께 맞춰야 한다. 운영 부하와 큐 대기시간 상한을 보장하는 부하 시험은 별도다.
- SDK v1·기존 Azure 두 경로에 통신 시간초과/500 응답을 넣어, 기록된 호출 하나가 실제 HTTP 요청 하나만 보내고 오류를 반환하는 4개 검사를 추가했다.
- 빈 입력의 첫 질문은 별도로 소재 선택 전의 불필요한 확정·증빙 집계를 줄였다. Windows 단독 재현 1.223초 → 수정 후 0.808 / 0.868 / 0.839초. 후보·근거·우선순위는 기존 전체 평가와 같은지 4개 사례로 비교했다. 법 규칙과 질문 선택식은 변경하지 않았다.

## 2026-11-18 추출 프롬프트 캐시와 응답 추론 강도

`scripts/turn_latency.py --runs 3`(실제 Azure, 같은 배포)에 호출별 토큰 표(입력·캐시 적중·출력·그중 추론)를 넣고 쟀다. 토큰 수는 실행마다 거의 같고, 시간은 Azure 편차가 커서(같은 턴 1.7~12.9s) 참고값이다.

- **프롬프트 캐시는 메시지 단위로 맞는다.** 추출 호출당 입력 약 12,800토큰 중 이전에는 시스템 지침(1,686토큰)만 매 턴 할인됐다. 사용자 메시지 안에서 고정 자료를 앞으로 옮겨도 그대로였다(31%→32%). 고정 자료(설명 자료 목록, internal이 아닌 사실 목록)를 시스템 메시지로 옮기자(`build_system_prompt`, 프롬프트 m3.4) 첫 호출 뒤 매 턴 약 12,640토큰이 캐시됐다(평균 31% → 87%).
- 추출 평가(`scripts/eval_extractor.py`, 기존 질의회신 60건) 같은 날 비교: 이전 값 일치 17/59·소재 또는 분류 24/48·틀린 분류 0·guard 거부율 0.039 → 이후 18/59·21/48·0·0.0. 실행 사이 흔들림 범위 안이다.
- **응답 추론 강도 low는 쓰지 않는다.** 추론 토큰은 82→15로 줄었지만 문장이 검사(guard)에 걸린 재시도가 턴 12개 중 3번 생겨 응답 평균이 3.2s→5.3s로 늘었다. 응답 입력(약 780토큰)은 캐시 최소 길이보다 짧아 캐시되지 않는다. 응답 설정(`RESPOND_REASONING_EFFORT`)은 기본 비움(모델 기본값).
- **추출 추론 강도** (시스템 메시지 배치 위, 각 1회): low/medium/high 순으로 추출 평균 4.1/5.8/8.1s, 추론 토큰 125/229/457, 값 일치 16/21/20(59), 소재 또는 분류 22/23/25(48), 종류 외 사실 6/8/9(11), 틀린 분류 0. 기본값의 추론 토큰(270)은 medium과 비슷하다. medium이 균형이 가장 좋아 추출 기본값을 medium으로 정했다(`EXTRACT_REASONING_EFFORT`).

아래 표는 과거 측정값으로 보존한다.

- 스크립트: `uv run python scripts/turn_latency.py --runs 3 --db postgresql+psycopg://wd:wd@localhost:55432/waste_diagnosis`
- 환경: Windows 노트북, 엔진 1 프로세스, PostgreSQL 17(docker compose), Azure AI Foundry 배포(추론 모델), 요청 1개씩(동시 부하 없음)
- 시나리오: PP 문진 자유 입력 3턴 + 버튼 1턴, 3회 반복

## 서버 타임아웃 제안

- 기존 분류 호출의 12초는 정상 턴(최대 8.2s)은 넘기지만 여유가 작다. AI가 느린 시간대에는 넘을 수 있다.
- **제안: 새 엔진 경로는 30초.** 넘으면 서버는 "응답이 늦어요, 다시 보내 주세요"로 안내하고, 같은 요청을 다시 보내기 전에 `GET /cases/{id}`로 그 턴이 저장됐는지 확인한다(엔진은 턴을 끝까지 처리하고 저장한다).
- 당시 엔진 구성: AI 호출 하나는 `LLM_TIMEOUT_SECONDS`(기본 60초)와 SDK 재시도 2번을 썼다. 최악의 경우가 서버 타임아웃보다 길 수 있었다. 위 2026-11-17 절에서 SDK 중첩 재시도와 통합 대기 설정을 수정했다. AI 호출이 실패하면 엔진은 버튼 답변용 기본 문장(템플릿)으로 턴을 끝낸다.

## 측정하지 않은 것

동시 요청이 많을 때의 지연은 [sync-vs-async.md](sync-vs-async.md)(모의 AI 지연)를 본다. 실제 Azure 쿼터(분당 요청·토큰 수) 한도에서의 지연은 재지 않았다.
