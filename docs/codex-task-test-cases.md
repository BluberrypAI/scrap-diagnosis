# Codex 작업 지시서 4 — 계산기 검증용 사례 데이터 수집

이 작업은 **계산기가 맞는 답을 내는지 시험할 실제 사례를 공개 자료에서 모으는 일만** 한다.
코드 작성, 규칙 만들기, 계산기의 기대 출력 정하기는 하지 않는다.

## 다른 작업과 겹치지 않게

- 다른 작업(지시서 3)이 동시에 `audit/` 폴더를 쓰고 있다. **`data/`, `audit/`, `docs/`의 기존 파일은 읽기만 한다.**
- 이 작업의 결과는 **`testdata/` 폴더에만** 쓴다.
- 새로 받은 원본은 `sources/raw/` 아래 **`tc-` 로 시작하는 파일 이름**으로 저장한다. 기존 파일을 덮어쓰지 않는다.

## 왜 모으나

계산기는 폐기물의 사실(발생원, 상태, 재질, 형태, 오염, pH 등)을 받아 분류번호를 내거나, 정할 수 없으면 멈춘다.
이것이 맞는지 보려면 **"이런 사실이면 공식 기관이 이 번호라고 답했다"**는 사례가 필요하다.
특히 다음 두 종류가 모두 필요하다:
- 기관이 번호를 **분명히 답한** 사례 → 계산기가 같은 번호를 내야 함
- 기관이 **"시험해 봐야 안다", "사안별 판단"**처럼 답을 유보한 사례 → 계산기도 멈춰야 함

## 절대 규칙

1. 원문에 없는 사실을 만들지 않는다. 질의에 없는 사실은 `UNKNOWN`으로 둔다. 업종이나 상식으로 채우지 않는다.
2. 질의와 회신은 원문 그대로 인용한다. 요약 금지. 공백·줄바꿈 정리만 허용.
3. **기관의 결론을 그대로 옮긴다.** 기관이 번호를 말하지 않았으면 번호를 추론해서 넣지 않는다.
4. 출처는 정부·공공기관·법원 공개 자료만. 블로그·기사·민간 컨설팅 금지.
5. **실제 회사명·사업장명·주소·담당자 이름 같은 개인·기업 식별 정보는 옮기지 않는다.** 원문에 있으면 `[업체]`처럼 가린다.
6. 모든 행에 출처 URL, 문서명, 쪽, 회신일(없으면 `NOT_FOUND`), 확인일을 붙인다.
7. 모든 행의 `review_state`는 `UNVERIFIED`.
8. 검색했으면 어디서 무엇으로 검색했는지 기록한다.

## 사례마다 기록할 것

### `testdata/cases_raw.csv` — 원문 그대로

`case_id, source_id, doc_title, page_or_url, answered_on, agency, law_version_at_time, question_quote, answer_quote, set(MAIN/PERIPHERAL/OUT_OF_SCOPE), related_codes_mentioned, searched_via, checked_on, review_state`

- `related_codes_mentioned`: 질의나 회신에 **글자로 나온** 번호만. 추론 금지.

### `testdata/cases_facts.csv` — 질의에 나온 사실만 뽑은 것

`case_id, fact, value, quote`

`fact`는 아래 목록에서만 고른다. 원문에 근거 구절이 없으면 그 fact 행을 만들지 않는다.

| fact | value 예시 |
|---|---|
| source_type | factory / construction / medical / household / other |
| is_waste_claim | 재투입 / 판매 / 부산물 / 순환자원 / 없음 |
| waste_family | plastic / metal / acid / alkali / oil / solvent / sludge / other |
| physical_state | solid / liquid / gel / sludge |
| material | PP / PE / PET / PVC / PU / PS / 고무 / 철 / 스테인리스 / 알루미늄 / 구리 / 염산 / 황산 / 질산 / 불산 / NaOH / KOH / 암모니아 / 기타(원문 표기) |
| form | 조각·러너·불량품 / 포장재(사용 전) / 포장재(사용 후) / 발포체 / 어망 / 부자 / 전선 / 절삭칩 / 판재·부품 / 캔 / 용기·드럼 / 혼합 |
| process | 원문에 적힌 공정명 그대로 |
| contamination | 기름 / 절삭유 / 페인트 / 용제 / 약품 / 없음 / 원문 표기 |
| ph | 숫자 (원문 그대로) |
| oil_content_pct | 숫자 |
| test_done | 원문에 적힌 시험 항목 |
| mixed_with | 섞인 폐기물 (원문 표기) |
| lcd_semiconductor_process | Y / N |

목록에 없는 사실이 판단에 중요하면 `fact=other`, `value`에 원문 표기를 그대로 쓴다.

### `testdata/cases_answer.csv` — 기관이 내린 결론

`case_id, answer_type, answered_code, answered_designated, conditions_quote, answer_quote`

`answer_type`는 회신 문구에 따라 하나만:
- `CODE_GIVEN` — 번호를 분명히 답함
- `CODE_CONDITIONAL` — "~라면 ○○번" 처럼 조건부로 답함 (조건 문구를 `conditions_quote`에)
- `DESIGNATED_ONLY` — 지정/일반 여부만 답함
- `NOT_WASTE` — 폐기물이 아니라고 답함
- `TEST_REQUIRED` — 시험·분석 결과에 따라 다르다고 답함
- `CASE_BY_CASE` — 사안별·관할 기관 판단이라고 답함
- `OTHER` — 위에 안 맞음

`answered_code`는 회신에 **글자로 나온** 번호만. 회신이 번호 없이 이름만 말했으면 비워 두고 `answer_quote`에 남긴다. 이름을 번호로 바꾸지 않는다.

## 짝 사례 표시

같은 재질인데 형태만 다르거나, 같은 폐기물인데 pH·오염만 다른 사례처럼 **사실 하나 차이로 답이 갈리는 사례 쌍**을 찾으면 `testdata/case_pairs.csv`에 기록한다.

`pair_id, case_id_a, case_id_b, differing_fact, note`

## 개발용·평가용 나누기

계산기 규칙을 만들 때 본 사례로 계산기를 평가하면 점수가 부풀려진다. 그래서 미리 나눈다.

- `testdata/split.csv` — `case_id, split(DEV/EVAL)`
- **같은 문서·같은 사례 번호에서 나온 질의는 같은 쪽에 둔다.**
- 이미 규칙 근거로 쓴 사례(2023 해설서 p.117 사례 1·2, p.118 스펀지 사례, 원주 사례 52·56·63)는 **DEV**.
- 나머지는 출처 문서 단위로 섞어 약 절반을 EVAL로 둔다. EVAL 문서 목록을 보고서에 적는다.
