# 진단 엔진 연동 안내 (팀원용)

> 2026-11-09 기준. 진단 엔진(`waste-diagnosis`)을 서버·웹·AI에 붙일 때 알아야 할 것을 쉽게 정리했습니다.
> 자세한 규칙은 마지막 절의 문서를 보면 됩니다. 이 문서만 읽어도 "내가 뭘 해야 하는지"는 알 수 있게 썼습니다.

## 0. 세 줄 요약

1. 진단 엔진은 **"이 폐기물의 분류번호가 뭔지"를 묻고 답하며 정해 주는 서비스**입니다. 서버(scrap-server)만 엔진을 부릅니다.
2. 엔진이 결과를 확정하면 **인계 객체(handoff)** 라는 JSON을 만듭니다. 경로추천 AI(scrap-ai)는 이것만 보고 다음 단계를 정하면 됩니다.
3. 각 팀이 할 일은 4절에 역할별 체크리스트로 있습니다. 같이 정해야 할 것은 6절에 있습니다.

## 1. 엔진이 하는 일

### 전체 그림

```
 사용자
   │  (화면에서 답변·서류 올리기)
   ▼
 scrap-web ──────▶ scrap-server ──────▶ 진단 엔진 ──(문장 이해만)──▶ Azure OpenAI
 (화면)            (로그인·권한 확인)     (분류번호 판정)
                        │                    │
                        │◀── 확정 결과 ───────┘
                        ▼
                    scrap-ai (경로추천)
```

- **웹은 엔진을 직접 부르지 않습니다.** 항상 서버를 거칩니다. 엔진 주소와 비밀 토큰은 서버만 압니다.
- 엔진은 사용자에게 **꼭 필요한 질문만 하나씩** 합니다. 사용자가 처음에 많이 말해 주면 질문이 줄어듭니다.
  - 예: "PP 사출 스크랩이고 고체예요"라고 하면 소재·상태 질문을 건너뜁니다(PP 사례에서 10문항 → 4문항).

### 엔진의 원칙: "AI는 제안하고, 규칙이 판정하고, 서버가 검증한다"

| 누가 | 무엇을 | 무엇을 **안** 하나 |
|---|---|---|
| AI(Azure OpenAI) | 사용자 말에서 "소재 = PP" 같은 값을 뽑고, 질문 문장을 자연스럽게 다듬음 | 분류번호를 정하지 않음 |
| 규칙 엔진 | 법령 기반 규칙표로 분류번호를 정함 | 추측하지 않음. 모르면 다시 물음 |
| 서버(엔진의 API) | AI가 뽑은 값이 사용자 말에 실제로 있는지, 확정 직전에 결과가 맞는지 다시 검사 | - |

그래서 AI가 엉뚱한 답을 내도 분류번호가 틀리게 나오지는 않습니다. AI가 꺼져 있어도 버튼 답변만으로 끝까지 진행할 수 있습니다.

## 2. 용어 풀이

| 용어 | 뜻 | 예시 |
|---|---|---|
| 건(case) | 폐기물 한 묶음에 대한 진단 1건 | "3공장 PP 스크랩 11월분" |
| 문진 | 엔진이 질문하고 사용자가 답하는 과정 | "기름이 묻어 있나요?" |
| 사실(fact) | 판정에 쓰는 값 하나 | `material = pp`, `oil_content_pct = 2` |
| 사실 상태 | 그 값을 얼마나 믿을 수 있는지 | `CLAIMED`(사용자가 말함), `EVIDENCED`(서류로 확인), `DECLARED_UNKNOWN`(모른다고 함) |
| 서류 값 후보 | 서류에서 읽었지만 **아직 검수 전인 값**. 판정에 안 씀 | 상태 `UNVERIFIED` |
| 검수 / 적용(apply) | 사람이 서류 값을 확인하고 엔진에 "이 값 써도 돼"라고 보내는 것 | 적용하면 `EVIDENCED`가 됨 |
| 효력 해제(revoke) | 적용했던 서류 값을 판정에서 빼는 것. 기록은 남음 | 서류를 잘못 올렸을 때 |
| 분기(branch) | 이번 턴에 화면이 해야 할 일 | 질문, 서류 요청, 결과 확인 등 (4-2절 표) |
| 확정(confirm) | 사용자가 결과를 받아들이는 것. 이후 수정하려면 다시 열기(reopen) | 상태 `CODE_CONFIRMED` |
| 인계 객체(handoff) | 확정 결과를 경로추천 AI에 넘기는 JSON | 5절 |
| 규칙 버전(kb_version) | 판정에 쓴 규칙표의 버전 | 규칙표가 바뀌면 달라짐 |
| 서비스 토큰 | 서버가 엔진을 부를 때 쓰는 비밀번호 같은 값 | `Authorization: Bearer …` |
| 409 | "요청은 맞는데 지금 상태에서는 못 한다"는 HTTP 응답 | 이미 확정된 건에 답변을 보냄 |

## 3. 한 건이 처리되는 순서

서버 입장에서 부르는 순서입니다. 모든 경로 앞에 `/internal/v1`이 붙습니다.

| 순서 | 하는 일 | 엔진 API |
|---|---|---|
| ① | 건 만들기 + 첫 질문 받기 | `POST /cases` |
| ② | 사용자 답변 보내기 → 다음 질문 받기 (반복) | `POST /cases/{id}/diagnosis/messages` |
| ③ | (필요하면) 서류 올리기 → 값은 **후보**로 저장 | `POST /cases/{id}/documents` |
| ④ | (필요하면) 사람이 검수한 값 적용 → 판정에 반영 | `POST /cases/{id}/documents/{doc}/values/apply` |
| ⑤ | 결과가 나오면(`FINAL_REVIEW`) 사용자가 확정 | `POST /cases/{id}/confirm` |
| ⑥ | 응답의 `handoff`를 경로추천 AI로 전달 | (서버 → scrap-ai) |
| ⑦ | 고치고 싶으면 다시 열기 → ②로 | `POST /cases/{id}/reopen` |

매 요청에 붙이는 헤더는 두 개입니다.

```
Authorization: Bearer <ENGINE_SERVICE_TOKEN>   ← 서버만 아는 비밀값
X-Company-Id: <서버의 기업 ID>                 ← 로그인한 사용자의 기업
```

다른 기업의 건을 부르면 엔진은 "없음(404)"으로 답합니다. 기업끼리 서로의 자료를 볼 수 없습니다.

## 4. 역할별 할 일

### 4-1. 서버 (scrap-server)

- [ ] **엔진 연결 정보는 서버에만 두기.** 엔진 주소와 `ENGINE_SERVICE_TOKEN`은 서버 환경변수에 둡니다. 브라우저 코드에 넣으면 누구나 다른 기업 자료를 볼 수 있게 됩니다.
- [ ] **review와 엔진 건 연결하기 (S1).** 서버의 review ID와 엔진의 `case.id`를 저장합니다. 같은 "시작" 요청이 두 번 와도 건이 두 개 생기지 않게 막아 주세요(버튼 두 번 클릭, 재전송).
- [ ] **타임아웃 늘리기.** 기존 분류 호출의 타임아웃은 12초입니다. 새 엔진은 한 턴에 AI를 최대 2번 부릅니다(값 뽑기, 문장 다듬기). 실제로 재 보니 한 턴에 보통 4.4초, 가장 길 때 8.2초가 걸렸습니다. 12초는 여유가 작아서 **30초**를 제안합니다. 시간이 넘어 다시 보낼 때는 먼저 `GET /cases/{id}`로 그 턴이 이미 저장됐는지 확인해 주세요(엔진은 늦더라도 턴을 끝까지 처리합니다).
- [ ] **오류는 `detail.code`로 구분하기.** 엔진 오류는 항상 `{"detail": {"code", "message", "details"}}` 모양입니다. 서버 공통 오류 형식으로 바꿀 때 `code`를 그대로 쓰면 됩니다. 서버가 처리해야 하는 코드는 아래와 같습니다.

| code | 뜻 | 서버가 할 일 |
|---|---|---|
| `KB_CHANGED` (409) | 그 사이 규칙표가 업데이트됨 | `POST …/rebase` 호출 후 같은 요청을 다시 보냄 |
| `CONCURRENT_UPDATE` (409) | 다른 요청이 먼저 같은 건을 고침 | 건을 다시 조회하고 다시 시도 |
| `CASE_NOT_DIAGNOSABLE` (409) | 이미 확정된 건 | 사용자에게 "다시 열기"를 안내 |
| `DOCUMENT_VERSION_MISMATCH` (409) | 검수하는 동안 서류 파일이 교체됨 | 최신 파일로 다시 검수 |
| `VALIDATION_ERROR` (422) | 값 형식이 틀림 | `details.problems`의 항목별 이유를 화면에 보여 줌 |
| `CASE_NOT_FOUND` (404) | 없거나 다른 기업의 건 | 404로 그대로 |

- [ ] **서류 검수 흐름 연결하기 (S3).** 서버의 기존 업로드·검수·교체 API를 그대로 씁니다. 사람이 검수를 끝내면 엔진 `values/apply`로 보냅니다. 파일을 바꾸면 엔진 `versions`, 검수를 취소하면 `revoke`를 부릅니다.
- [ ] **기업 정보는 "사용자가 확인한 값"만 보내기 (S4).** 회사 기본값(예: "평소 PP를 배출함")을 그대로 보내면 안 됩니다. "이번 건도 PP가 맞나요?"를 사용자가 확인한 뒤 `confirmed_facts`로 보내고, 버전을 `company_profile_version`에 넣습니다. 회사명·주소·연락처는 보내지 않습니다.
- [ ] **새 결과용 검증 추가하기 (S5).** 새 엔진은 "분류번호 없음(`NO_CODE`)" 결론도 확정합니다(예: 폐기물 아님). 기존 분류 기록 검증에 그대로 넣으면 거부되니, 새 결과용 검증을 따로 둡니다. 확정됐다고 바로 처리 업체 추천을 허가하면 안 됩니다.
- [ ] **판정이 바뀌면 이전 추천을 "오래됨"으로 표시하기 (S6).** reopen 뒤 다시 확정하면 판정 버전 번호가 올라갑니다. 이전 버전으로 만든 추천은 쓰지 않게 막아 주세요(삭제는 하지 않음).
- [ ] **탈퇴 시 엔진 데이터도 지우기 (S7).** 유예 기간이 끝나면 `DELETE /internal/v1/companies/{기업ID}/data`를 부릅니다. 응답 `status`가 `DONE`일 때만 완료로 기록하고, 실패하면 다시 부릅니다(여러 번 불러도 안전).
- [ ] (참고, 엔진과 무관) 코드 분석에서 나온 개선점입니다.
  - 서류 업로드·교체·추가 자료 저장이 `async def` 안에서 동기 파일 쓰기를 합니다. 파일 작업만 `asyncio.to_thread`로 빼면 됩니다.
  - 시설 검색은 외부 검색을 기다리는 동안 DB 트랜잭션을 열어 둡니다. DB 연결 풀이 작아서(5+10) 요청이 몰리면 연결이 모자랄 수 있습니다.

### 4-2. 웹 (scrap-web)

- [ ] **문진 화면으로 동작과 형식 확인하기.** 문진 화면은 scrap-web(`/wastes/case-<건 ID>/survey`)에 있습니다. 예전 참조 화면(`web/`)은 scrap-web으로 옮긴 뒤 지웠고, 원본은 `archive/reference-web-ui` 브랜치에 있습니다. 안내는 [ui/handover.md](../ui/handover.md)에 있습니다.
- [ ] **테스트용이라 실제와 다른 점 알아 두기.** 참조 화면은 엔진을 직접 부르고, 개발용 회사 선택 화면이 있습니다. 서류 값은 검수 창(왼쪽 원문 · 오른쪽 읽은 값)에서 확인해 "검수 완료"로 적용합니다. 원문은 브라우저에만 보관합니다(엔진은 원문을 보관하지 않음). 실제 scrap-web은 서버만 부르고, 로그인과 서버의 검수 화면을 씁니다.
- [ ] **분기(`branch`)마다 다른 카드를 보여 주기.** 응답의 `branch` 값 하나로 화면이 결정됩니다.

| branch | 화면 |
|---|---|
| `ASK_FACT` | 질문 카드 하나(버튼 또는 입력칸). 입력창으로 말해도 됨 |
| `REQUEST_EVIDENCE` | 서류 요청 카드(어떤 서류로 무엇을 확인하는지) |
| `RESOLVE_CONFLICT` | "말한 값과 서류 값이 달라요" 카드 |
| `FINAL_REVIEW` | 결과 카드 + 확정 버튼 |
| `UNSUPPORTED` | "지금은 판정할 수 없어요" 카드 |

- [ ] **보충 설명 말풍선 보여 주기.** 사용자가 "왜 물어봐요?", "용출이 뭐예요?"라고 물으면 턴 응답에 `assist`가 옵니다(평소에는 null). `assist.text`를 질문 말풍선 앞에 보여 주고, `sources`는 "근거 보기", `terms`는 "용어 설명"으로 접어 두세요. 질문 카드는 그대로입니다. 서버는 `assist`를 가공 없이 넘기면 됩니다.
- [ ] **결과 카드에 추정 안내 보여 주기.** 결과 응답의 `result.assumptions`에 시험이 아니라 답변으로 추정한 내용이 오면 결론 아래에 눈에 띄게 보여 주세요(참조 화면은 노란 안내 상자).
- [ ] **질문 카드에 용어 설명 보여 주기.** 질문 응답의 `question.terms`에 그 질문에 나온 전문용어(용출, 고형물함량 등)의 쉬운 설명 `[{term, plain, example}]`이 옵니다. AI가 만든 글이 아니라 사람이 쓴 고정 설명입니다. 참조 화면은 "용어 설명" 접기로 보여 줍니다.
- [ ] **서류 검수 화면 만들기 (W3).** 엔진은 서류 원문과 값을 비교하지 않습니다(6절 1번). 그래서 **사람이 원문을 보며 값을 확인하는 화면**이 실제 안전장치입니다. 원문 위치, 값, 단위, 검수 상태를 보여 주고, 값을 고치면 다시 검수하게 해 주세요.
- [ ] **"확정"과 "처리 업체 찾기"를 구분하기 (W4).** 분류 확정은 처리 업체가 받아 준다는 뜻이 아닙니다. 결과 카드에 있는 "검토 전 규칙 · 참고용" 표시는 지우지 말아 주세요(모든 규칙이 아직 전문가 검토 전입니다).
- [ ] **계정을 바꾸면 이전 화면 상태 지우기 (W5).** 다른 기업 계정으로 로그인했을 때 이전 기업의 초안이 보이면 안 됩니다.

### 4-3. 경로추천 AI (scrap-ai)

- [ ] **인계 객체(`diagnosis-handoff-v1`) 받기.** 확정되면 서버가 이 JSON을 넘겨줍니다. 두 필드로 분기하면 됩니다.

| result_type | route_guidance.action | 할 일 |
|---|---|---|
| `WASTE_CODE` | `RECOMMEND_ROUTE` | 분류번호로 처리 경로·업체 추천 |
| `NO_CODE` | `NO_ROUTE_NEEDED` | 폐기물이 아니거나 순환자원 → 처리 경로 불필요 안내 |
| `NO_CODE` | `REFER_OTHER_LAW` / `REFER_MUNICIPALITY` / `REFER_AUTHORITY` | 다른 법, 지자체, 관할 기관으로 안내 |
| `NO_CODE` | `NEEDS_TEST` | 분석기관 시험 안내 |
| `NO_CODE` | `MANUAL_CLASSIFICATION` | 담당자 확인 필요 안내 |

- [ ] **"검토 전 규칙" 표시 유지하기.** 인계 객체의 `review`가 `UNVERIFIED`이면 사용자 안내에도 그 사실을 보여 주세요.
- [ ] **재활용 유형(R코드)은 엔진이 주지 않습니다 (D).** 엔진은 분류번호까지만 정합니다. 기존 서버의 첫 공정 조회는 R코드와 투입 형태(스크랩·필름·병 등)를 요구하므로, 분류 뒤에 이를 확인하는 단계가 따로 필요합니다. 기본 R코드를 임의로 채우지 말아 주세요.
- [ ] **`assumptions`가 있으면 함께 안내하기.** 시험·서류가 아니라 사용자 답에서 추정한 내용(예: "PCB 관련 없음" → PCB 기준 미만으로 추정)이 문장 목록으로 옵니다. 처리 업체 안내 때 "시험으로 확인하지 않은 항목"으로 알려 주세요.
- [ ] 사실마다 출처(`source_type`)가 붙어 있습니다. `DOCUMENT`는 서류로 확인한 값, `UTTERANCE`는 사용자가 말한 값, `PROFILE_CONFIRMED`는 사용자가 확인한 기업 정보입니다.

## 6. 왜 이렇게 만들었나

### 1) 엔진은 서류 값이 맞는지 원문과 비교하지 않습니다

엔진은 숫자 "7"이 서류에 적힌 "2"를 잘못 옮긴 것인지 알 방법이 없습니다. 그래서 엔진은 **형식만** 거릅니다.

- 거르는 것: 빈 값, `-`, 숫자 칸의 글자(`"약 2"`, `"5mg"`), 선택지에 없는 값, 단위가 다른 값
- 거르지 않는 것: 값 자체가 맞는지

값이 맞는지는 **사람의 검수**가 책임집니다. PDF·이미지를 올리면 엔진이 시험성적서 표에서 값을 자동으로 읽어 후보로 채워 두지만(값 옆 메모에 "몇 쪽 몇 행 몇 열"에서 읽었는지 적힘), 이 값도 사람이 원문과 비교해 확인한 뒤에만 판정에 쓰입니다.

### 2) DB를 동기 방식으로 두었습니다

팀 기술스택 문서에는 "비동기"라고 되어 있지만, 엔진은 지금 동기 방식입니다. 이유는 세 가지입니다.

1. **팀 코드도 모두 비동기는 아닙니다.** 코드를 분석해 보니 scrap-server는 DB·HTTP가 비동기지만 파일 작업 일부는 동기였습니다. scrap-ai는 동기이고, 자기 문서에도 그렇게 적혀 있습니다. 서버 ADR도 "AI 쪽 구성은 그 저장소에서 정한다"고 나눠 두었습니다.
2. **성능 차이가 거의 없었습니다.** 식당으로 비유하면, 비동기는 "직원 한 명이 여러 테이블을 돌아가며 서빙"하고, 동기는 "테이블마다 직원 한 명"입니다. 손님(동시 요청)이 직원 수보다 많으면 동기는 줄을 섭니다. 그런데 직원 수(스레드)를 200명으로 늘리면 차이가 사라집니다. 실제로 재 보니 동시 200턴에서 4.3초 vs 4.4초로 거의 같았습니다. 자세한 측정은 [perf/sync-vs-async.md](../perf/sync-vs-async.md)에 있습니다.
3. **진짜 병목은 따로 있습니다.** 손님이 많아지면 먼저 막히는 곳은 서버가 아니라 Azure OpenAI 사용량 한도(분당 요청 수·토큰 수)일 가능성이 큽니다.

> 주의: `async def`로 이름만 바꾸고 안에서 동기 작업을 하면 오히려 서버 전체가 멈춥니다. 엔진에서 실제로 이 버그(서류 업로드)를 찾아 고쳤습니다.

운영용 PostgreSQL은 이 동기 방식으로 붙였습니다(`psycopg`). PostgreSQL에서도 전체 테스트가 통과합니다. 문진 한 턴이 AI 답을 기다리는 몇 초 동안은 DB 연결을 놓아서, 연결 수가 적어도 동시 문진이 막히지 않게 했습니다.

### 3) AI에 보내기 전에 개인정보를 가립니다

사업자·법인·주민번호, 전화번호, 이메일, 상세주소는 AI로 보내기 전에 가립니다. 가리는 과정에서 오류가 나면 AI로 보내지 않고 버튼 답변으로 진행합니다. 서류 원문은 기본적으로 AI에 보내지 않습니다. 기록(Trace)에도 가린 문장만 남습니다.

| # | 질문 | 엔진 쪽 제안 |
|---|---|---|
| 1 | 엔진 DB를 비동기로 바꿔야 할까? | 동기 방식으로 PostgreSQL까지 붙여 두었음. 꼭 필요하면 전환(1~1.5일) |

| 7 | 서버 → 엔진 타임아웃은 몇 초로 할까? | 30초(실측: 보통 4.4초, 최대 8.2초) |

### API 형식 변경 — 서버 담당자 확인 필요

팀 규칙(1장)상 필드·엔드포인트 **추가**는 자유지만, 기존 형식의 **삭제·이름·타입 변경**은 호출하는 쪽과 합의하고 이슈에 기록해야 합니다. 이번 작업에서 아래가 해당합니다. 아직 엔진을 실제로 부르는 서버 코드는 없어서 깨지는 곳은 없지만, 확인을 받아 두려고 남깁니다.

| # | 무엇이 바뀌었나 | 이전 | 지금 | 왜 |
|---|---|---|---|---|
| A1 | 422(입력 형식 오류)의 `detail` **타입** | 목록 `[{"loc", "msg", "type"}]` | 객체 `{"code": "VALIDATION_ERROR", "message", "details": {"errors": [...]}}` | 모든 오류를 같은 모양으로 맞춰서 서버가 `code` 하나로 처리하도록. 서버 공통 오류 명세와 같은 구조 |
| A2 | 서류 업로드의 `facts` **동작** | 올리면 바로 증빙(EVIDENCED)으로 판정에 쓰임 | 검수 대기 후보(UNVERIFIED)로만 저장. `values/apply`로 검수 결과를 보내야 판정에 쓰임 | 검수 전 값이 판정에 쓰이지 않게(DOC-002). 응답에 `values`가 추가됨 |
| A3 | 오류 응답에 `code`·`details` **추가** | `{"detail": {"message", …}}` | 같은 객체에 `code`·`details` 추가(기존 키 유지) | 추가라 합의 대상은 아니지만 서버가 쓸 필드라 알림 |
| A4 | 서버용 경로 `/internal/v1/...`와 서비스 토큰 **추가** | 없음 | 서버는 이 경로만 부름 | 기업 간 데이터 분리(CORP-007). 루트 경로는 개발·참조 화면용 |
| A7 | 턴 응답 `assist`, 대화 기록 `conversation[].assist` **추가** | 없음 | "왜?", "뭐예요?" 질문에 근거 조문·용어로 답하는 보충 설명 | 추가라 합의 대상은 아니지만 화면이 쓸 필드라 알림 |
| A6 | 질문 카드 `question.terms`, 결과 카드 `result.assumptions`, 인계 객체 `assumptions` **추가** | 없음 | 용어 설명, 답변 기반 추정 안내 | 추가라 합의 대상은 아니지만 화면·경로추천이 쓸 필드라 알림 |
| A5 | 판정·인계 객체 `review`에 **값 추가** | 항상 `UNVERIFIED` | `UNVERIFIED` 또는 `VERIFIED`(전문가 검토 완료) | 도메인 전문가 규칙 검토 결과를 반영(`knowledge/README.md`). 새 값을 모르는 쪽은 `UNVERIFIED`가 아니면 검토 완료로 보면 된다 |

서버 ↔ 엔진 형식 변경은 서버 담당자 리뷰 승인 후 반영하는 규칙(1장)이 있으므로, A1·A2는 서버 담당자가 [api/server-engine-contract.md](../api/server-engine-contract.md)를 보고 확인해 주세요.
