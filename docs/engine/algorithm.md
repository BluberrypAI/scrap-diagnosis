# 진단 엔진 알고리즘

폐기물 분류번호를 정하는 엔진이 안에서 어떻게 움직이는지 설명한다. 1절은 개발자가 아니어도 읽을 수 있게 썼고, 2절부터는 코드와 1:1로 맞는 정확한 규칙이다. 코드 주석의 "algorithm.md N절"은 이 문서의 절 번호다.

| 절 | 내용 | 코드 |
|---|---|---|
| 1 | 한눈에 보기 | - |
| 2 | 규칙 데이터 | `app/rules/model.py`, `app/rules/loader.py`, `data/` |
| 3 | 사실과 유효 사실 | `app/domain/facts.py`, `app/domain/ranges.py` |
| 4 | 3값 평가와 확정 | `app/rules/evaluator.py` |
| 5 | 질문 고르기 | `app/rules/selector.py` |
| 6 | 분기와 충돌 | `app/agent/router.py`, `app/rules/conflicts.py` |
| 7 | 한 턴의 처리 순서와 AI의 역할 | `app/agent/orchestrator.py`, `extractor.py`, `guard.py`, `responder.py` |
| 8 | 확정·다시 열기·기록 | `app/api/service.py`, `app/domain/trace.py`, `app/domain/case.py` |
| 9 | 검증 방법 | `tests/`, `tools/legacy_regression.py`, `data/golden/` |
| 10 | 처음 설계와 달라진 점 | - |

## 1. 한눈에 보기

### 원칙
**AI(LLM)는 제안하고, 규칙 엔진이 판정하고, 서버가 검증한다.**
- AI는 사용자 말에서 "소재 = PP" 같은 값을 뽑고, 질문 문장을 다듬는 일만 한다.
- 분류번호는 법령을 옮긴 **규칙표**가 정한다. 같은 사실을 넣으면 언제나 같은 결과가 나온다.
- AI가 뽑은 값은 검사(guard)를 통과해야 규칙표에 들어간다.

### 한 턴의 흐름

```
 사용자 답변 ─┬─ 버튼 ──────────────────────────┐
             └─ 자유 입력 → AI 추출 → 검사(guard) ┤
                                               ▼
                                      사실 이력에 추가(덮어쓰지 않음)
                                               ▼
                         규칙표 평가(참·거짓·모름) → 남은 후보, 확정을 막는 사실
                                               ▼
                         분기 결정: 충돌? 판정 불가? 질문? 서류? 결과?
                                               ▼
                         (질문이면) 가장 많이 좁혀 주는 질문 하나 고르기
                                               ▼
                         AI가 문장 다듬기 → 검사 (실패하면 정해진 문장)
```

### 왜 질문이 적은가
예전 엔진은 정해 둔 질문을 모두 물었다. 새 엔진은 두 가지 규칙으로 질문을 줄인다.
1. **결론을 실제로 막고 있는 사실만 묻는다.** 어떤 값이 나와도 결론이 같으면 묻지 않는다.
2. **그중 후보를 가장 많이 줄여 주는 질문을 먼저 묻는다.** 스무고개에서 "동물이에요?"를 먼저 묻는 것과 같다.

또 "모두 해당 없음"처럼 한 번에 여러 사실을 확인하는 **묶음 질문**이 있다. 사용자가 처음에 많이 말하거나 기업 정보에 값이 있으면 그만큼 질문이 줄어든다.

PP 스크랩의 실제 진행(기업 정보에 "배출시설 있음"이 있을 때, 5절 예시와 같은 계산):

| 차례 | 엔진이 고른 질문 | 남은 후보 |
|---|---|---|
| 1 | 소재 분류 (13개 중) | 134 |
| 2 | 소재 (플라스틱·고무 안의 14개 중) | 134 |
| 3 | 묶음: 기름·잔류물·PCB·유해화학물질 "모두 해당 없음"? | 21 |
| 4 | 묶음: 내보내는 물질이고 순환자원·다른 법 대상 아님? | 5 |
| 5 | 물리적 상태(고체·액체·반고체) | 2 |
| 결과 | `51-03-01` 폐합성수지류 → 확정 검토 | 1 |

첫 메모에 "PP 고체예요"라고 쓰면 1·2·5번을 건너뛴다.

### 사용자가 분류번호를 먼저 말하면?
"51-03-01이에요"라고 해도 **바로 통과하지 않는다.** 엔진은 그 번호를 낼 수 있는 규칙과 관련된 질문의 점수를 1.5배로 올려(5.3절) 그 번호를 확인하는 질문을 먼저 할 뿐이다. 번호는 규칙이 조건을 확인한 뒤에만 정해진다.

## 2. 규칙 데이터

규칙은 코드가 아니라 데이터(YAML)다. 사람이 고치는 원본은 `knowledge/`(법 규칙·소재·번호 대응·공통 정의·사실 설정·용어집, 형식은 `knowledge/README.md`)이고, `data/real/`은 이것을 `tools/build_kb.py`로 빌드한 생성물이라 손으로 고치지 않는다. 질문 전략(대리 질문 `implies`, 보수 관계 `complement`)은 판정 조건과 분리해 사실 설정에 둔다(`app/rules/implications.py`). `data/sample/`은 테스트용 작은 규칙 세트다.

| 파일 | 내용 | `data/real` 규모 |
|---|---|---|
| `facts_catalog.yaml` | 사실 카탈로그: 물을 수 있는 사실과 값 영역 | 37개 |
| `rules/tables/*.yaml` | 소재별 규칙 테이블 | 97개 테이블, 규칙 3,534개 |
| `rules/common/*.yaml` | 여러 테이블이 함께 쓰는 규칙(적용 범위, 사업장 여부). 테이블이 `includes`로 넣는다 | - |
| `question_groups.yaml` | 묶음 질문 | 2개 |
| `codes.yaml` | 별표 4 분류번호표 | 313개 |
| `outcome_guidance.yaml` | 결론 → 경로추천 안내(`docs/handoff-contract.md`) | - |
| `sources.yaml` | 근거(법령·질의회신) 원문 | - |

### 2.1 사실 카탈로그(FactDef)
사실 하나의 정의다. 엔진은 카탈로그에 없는 사실은 받지 않는다.

| 필드 | 뜻 |
|---|---|
| `type` | `enum`(선택지) · `bool`(예/아니오) · `number`(숫자, `unit` 단위) |
| `values`, `value_labels` | enum 값과 화면 라벨 |
| `prior` | 값별 사전확률(예: 기름 없음 0.8). 없으면 나머지 값은 균등 |
| `ask_cost` | 묻는 비용(기본 1). 시험이 필요한 수치처럼 답하기 어려우면 크게 둔다 |
| `legal_priority` | 법적 중요도(기본 1). 지정폐기물 여부처럼 중요한 사실은 크게 둔다 |
| `evidence_type` | 이 사실을 증명하는 서류 종류(예: 시험성적서) |
| `none_value` | 묶음 질문에서 "모두 해당 없음"을 고르면 넣을 값 |
| `parent`, `value_parent` | 2단계 질문. 예: `material`(97개)의 상위 분류 `material_group`(13개) |
| `domain: referenced` | 선택지를 "아직 살아 있는 규칙의 조건에 나오는 값"으로 한정(별표 4 번호 선택) |
| `ask_last` | 확정을 막는 다른 사실이 남아 있으면 묻지 않음(번호 선택은 마지막에) |
| `auto_single` | 남은 선택지가 하나면 묻지 않고 채움 |
| `internal` | AI가 자유 입력에서 뽑지 않음. 직전 질문의 선택지로만 받음 |

### 2.2 조건식
규칙의 `when`은 조건(Cond)과 그 조합이다.
- **조건:** `{fact, op, value, min_status}`. `op`는 `eq` `ne` `in` `not_in` `lt` `lte` `gt` `gte` `exists`.
- **조합:** `all`(모두), `any`(하나라도), `not`(부정). 얼마든지 겹쳐 쓸 수 있다.
- **`min_status`:** 그 조건이 참이 되려면 필요한 사실의 최소 상태. 기본은 `CLAIMED`(말로 충분). 기름 함량 5% 이상처럼 시험으로 확인해야 하는 조건은 `EVIDENCED`(서류 필요)다.

### 2.3 규칙과 테이블
- **규칙(Rule):** `when` 조건이면 `then` 결론. 결론은 분류번호(`code`, `category`, `name`)이거나, 번호 없는 결론(`outcome`: 폐기물 아님·적용 제외·생활폐기물·해석 필요 등)이다. `priority`, 근거 `basis`, 검토 상태 `review`(지금은 모두 `UNVERIFIED`), 시행 기간이 있다.
- **테이블(Table):** 규칙 묶음. `applies_when`(이 테이블을 쓰는 조건, 예: `material = pp`)과 `hit_policy`가 있다.
  - `PRIORITY`: 참인 규칙 중 우선순위가 가장 높은 것을 고른다. `data/real`은 모두 이 방식이다.
  - `UNIQUE`: 참인 규칙이 하나여야 한다.
- **우선순위 대역**(`data/real`, `data/real/conversion_report.md`): 위에서부터 먼저 따진다.

| 대역 | priority | 내용 |
|---|---|---|
| SCOPE_S0 | 1100 | 순환자원·폐기물 아님 |
| SCOPE_S1 | 1000 | 폐기물관리법 적용 제외 |
| DESIGNATED | 500 | 지정폐기물 → 별표 4 지정 코드 |
| HOUSEHOLD | 400 | 사업장 조건이 모두 거짓 → 생활폐기물 |
| INTERPRET | 300 | 해석 필요(질의회신 근거) |
| GENERAL | 100 | 사업장일반폐기물 코드 |

- **시행일:** 규칙과 테이블은 시행 기간이 있다. 평가는 그 건의 법 기준일 `as_of`(대화를 시작한 날, Asia/Seoul)에 유효한 것만 쓴다.

## 3. 사실과 유효 사실

### 3.1 사실(Fact)
값 하나와 그 값을 얼마나 믿을 수 있는지(상태), 어디서 왔는지(출처)를 함께 갖는다.

| 상태 | 뜻 | 순위 |
|---|---|---|
| `UNKNOWN` | 아직 모름 | 0 |
| `DECLARED_UNKNOWN` | 사용자가 "모름"이라고 답함. 다시 묻지 않음 | 0 |
| `CLAIMED` | 사용자가 말함 | 1 |
| `EVIDENCED` | 서류로 확인(검수 완료) | 2 |

출처: `UTTERANCE`(말), `DOCUMENT`(서류), `PROFILE`·`PROFILE_CONFIRMED`(기업 정보), `SCREENING`(묶음 질문), `DERIVED`(엔진이 자동으로 채움), `SIMULATION`(질문 고를 때의 가정, 저장 안 함).

숫자 사실은 하나의 수 대신 **구간**(`NumRange`, 예: "300kg/일 이상")일 수 있다. 구간이 규칙 임계값에 걸쳐 있으면(예: "1~10%"인데 조건이 "5% 이상") 그 조건은 모름으로 본다.

### 3.2 사실 이력과 유효 사실
- 같은 키의 사실은 **덮어쓰지 않고 이력에 추가(append)**한다. 이력은 지우지 않는다.
- 평가에는 키마다 **유효 사실** 하나를 쓴다: 상태 순위가 높은 것(EVIDENCED > CLAIMED > 그 외), 같으면 최신. 시각까지 같으면 출처·값 순서로 정해 입력 순서와 무관하게 결과가 같다.
- **철회(retract):** 사용자가 "모름으로 되돌리기"를 누르면 그 키에 철회 행을 추가한다. 철회 행보다 먼저 기록된 진술(CLAIMED)은 무시한다. 서류 값(EVIDENCED)은 무시하지 않는다.
- **서류 효력 해제(revoke):** 서류를 교체하거나 검수를 취소하면 그 서류에서 온 키마다 해제 행을 추가한다. 해제 행보다 먼저 기록된 같은 출처의 서류 값은 무시한다. 출처가 `문서id`이면 모든 버전, `문서id@vN`이면 그 버전만 해당한다.

## 4. 3값 평가와 확정

### 4.1 조건 하나의 평가
조건마다 참(TRUE), 거짓(FALSE), 모름(UNKNOWN) 중 하나가 나온다. 모름이면 이유도 남긴다.

| 경우 | 결과 | 모름의 이유 |
|---|---|---|
| 유효 사실이 없거나, 상태가 UNKNOWN·DECLARED_UNKNOWN이거나, 값이 없음 | 모름 | `MISSING`(모르면 `DECLARED_UNKNOWN`) |
| 숫자 구간이 임계값에 걸침, 타입이 맞지 않음 | 모름 | `MISSING` |
| 값으로 거짓 | **거짓**(상태와 무관) | - |
| 값으로 참인데 상태가 `min_status`보다 낮음 | 모름 | `NEEDS_EVIDENCE`(서류 필요) |
| 그 외 | 참 | - |

값으로 거짓이면 말로만 해도 그 규칙을 지운다. "기름 없음"이라고 말하면 기름 관련 지정폐기물 규칙은 서류 없이 빠진다. 반대로 참으로 만들려면 `min_status`를 채워야 한다.

### 4.2 조합: Kleene 3값 논리

| `all` | `any` | `not` |
|---|---|---|
| 하나라도 거짓 → 거짓 | 하나라도 참 → 참 | 참 ↔ 거짓 |
| 모두 참 → 참 | 모두 거짓 → 거짓 | 모름 → 모름 |
| 그 외 → 모름 | 그 외 → 모름 | |

평가하면서 규칙마다 두 가지를 모은다.
- `unknown_facts`: 결과를 바꿀 수 있는 미확인 사실(모름인 조건들의 사실)
- `eliminated_by`: 결과를 정한 사실(거짓이면 지운 근거, 참이면 성립 근거)

### 4.3 테이블 고르기
1. 법 기준일에 유효한 테이블마다 `applies_when`을 평가한다(없으면 참).
2. 참이 하나 → 그 테이블을 평가한다(`SELECTED`).
3. 참이 둘 이상 → `AMBIGUOUS`(판정 불가).
4. 모두 거짓 → `NONE`(지원 범위 밖, 판정 불가).
5. 아직 모름이 있음 → `PENDING`. 테이블을 고르는 데 필요한 사실(예: 소재)이 확정을 막는 사실이 된다. 후보는 아직 가능한 테이블들의 후보를 합친 것이다.

### 4.4 후보와 확정(PRIORITY)
- **후보:** 거짓이 아닌 규칙의 결론을 결론별로 모은 것. 결론의 키는 분류번호, 번호가 없으면 `@사유`.
- **준비된 규칙:** 남은 미확인 사실이 모두 `ask_last`(별표 4 번호 선택)뿐인 규칙. 사실상 성립한 것으로 본다.
- **바닥(floor):** 참인 규칙과 준비된 규칙 중 가장 높은 우선순위. 바닥보다 낮은 후보는 결과가 될 수 없으므로 **살아 있는 후보**(`live_candidates`)에서 뺀다. 남은 후보 수는 이 살아 있는 후보 수다.
- **확정 조건:**
  1. 참인 규칙 중 가장 높은 우선순위 p의 결론이 하나뿐이어야 한다. 같은 p에서 결론이 둘 이상이면 동률(`tie`)이고 판정 불가다.
  2. 우선순위가 p 이상이면서 **다른 결론**을 내는 모름 규칙이 없어야 한다. 그런 규칙이 막는 규칙(blocker)이다.
  3. 같은 결론을 내는 위쪽 모름 규칙은 결과를 바꾸지 못하므로 막지 않는다.
  4. 가장 높은 후보가 준비된 규칙(번호 선택만 남음)이면 아직 확정하지 않는다. 번호 선택과, 선택지를 늘릴 수 있는 같은 대역 이상의 모름 규칙이 막는 규칙이 된다.
- **UNIQUE 테이블:** 참인 결론이 정확히 하나이고, 다른 결론을 내는 모름 규칙이 없을 때 확정한다.

### 4.5 확정을 막는 사실(blocking_facts)
막는 규칙들의 미확인 사실을 모은 것이다. 이유는 조건에서 온 것을 쓰되, "모름"이라 답한 사실에 증빙 종류가 있으면 `NEEDS_EVIDENCE`로 바꾼다(서류로 받을 수 있음). 한 사실에 이유가 섞이면 `MISSING`을 우선한다.

**질문은 오직 여기서만 고른다.** 미확인이어도 확정을 막지 않는 사실은 묻지 않는다. 이것이 질문을 줄이는 첫째 규칙이다.

## 5. 질문 고르기

### 5.1 질문 후보(pool)
1. 확정을 막는 사실 중 이유가 `MISSING`인 것.
2. `ask_last` 사실(번호 선택)은 막는 다른 사실이 남아 있으면 뺀다.
3. 사용자가 "모름"이라 답한 사실과 같은 서류로 확인할 사실은 뺀다(6.3절, 서류로 한 번에 받는다).
4. 묶음 질문: 묶음에 속한 사실 중 후보가 **2개 이상**이고, 사용자가 그 묶음을 이미 펼치지 않았으면 묶음 하나를 후보로 더한다.

### 5.2 선택지와 확률
- **enum:** 카탈로그 값. `referenced`면 막는 규칙(없으면 살아 있는 규칙)의 조건에 나오는 값만. 상위 분류를 알면 그 분류의 값만.
- **bool:** 예/아니오.
- **number:** 규칙에 나오는 임계값으로 수직선을 자르고, 모든 조건의 참·거짓이 같은 조각끼리 합친 구간들. 예: 조건이 `< 300`, `>= 300`뿐이면 "300 미만"과 "300 이상" 두 개.
- **확률:** `prior`에 있는 값은 그 확률, 나머지는 남은 확률을 균등하게 나눈 뒤 합이 1이 되게 맞춘다.
- 화면에는 이 선택지에 "모름"이 더해진다.

### 5.3 점수
선택지마다 "이 값이라면?"을 가정하고 규칙을 다시 평가해 남는 후보 수를 센다(확정이면 1).

```
gain  = ln N − Σ p_v · ln max(n_v, 1)      N: 지금 남은 후보 수, n_v: 값 v일 때 남는 후보 수
score = legal_priority × gain ÷ ask_cost × focus
```

- `gain`은 정보량이다. 후보를 많이, 확률 높게 줄일수록 크다. 어떤 답이 나와도 후보가 그대로면 0이다.
- `legal_priority`가 큰 사실(지정폐기물 판단 등)을 먼저, `ask_cost`가 큰 사실(시험 수치)을 나중에 묻는다.
- `focus`: 사용자가 분류번호를 말했으면, 그 번호를 내는 규칙이 쓰는 사실의 질문은 1.5, 나머지는 1.
- **묶음 질문:** 두 가정으로 계산한다. "모두 해당 없음"(각 사실에 `none_value`를 넣음, 확률 = 각 사실 none 값 확률의 곱)과 "해당 있음/모름"(아무것도 넣지 않음, 확률 = 1 − 앞의 확률). `legal_priority`는 묶음 안 사실의 최댓값이다.
- **2단계 질문:** 세부 사실(소재)의 상위 분류를 모르고 분류가 2개 이상 남아 있으면, 세부 사실 대신 상위 분류를 묻는다. 점수는 세부 값 가정의 결과를 분류별로 합쳐 계산한다(확률은 합, 남는 후보는 합집합). 상위 분류를 "모름"이라 답하면 세부 사실을 전체 선택지로 묻는다.

**고르기:** 점수가 가장 높은 질문. 같으면 `legal_priority`가 큰 것, 그다음 키 이름 순. 모든 점수가 0이면(어떤 질문도 후보를 줄이지 못하지만 아직 확정할 수 없음) 규칙을 가장 많이 해소하는 질문을 고른다(`fallback`).

### 5.4 예시: PP 3번째 질문
소재가 PP로 정해진 뒤 살아 있는 후보는 21개다(ln 21 = 3.045). 상위 후보 셋의 계산:

| 질문 | 선택지 → 남는 후보 | gain | legal | cost | score |
|---|---|---|---|---|---|
| 묶음 "기름·잔류물·PCB·유해화학물질" | 모두 해당 없음 → 5, 해당 있음/모름 → 21 | 0.972 | 3 | 1 | **2.917** |
| 기름 여부 | 없음 → 11, 있음 → 21 | 0.517 | 3 | 1 | 1.552 |
| 유해화학물질 폐기 | 예 → 21, 아니오 → 17 | 0.205 | 3 | 2 | 0.307 |

묶음의 "모두 해당 없음" 확률은 0.9(잔류물 없음) × 0.8(기름 없음) × 0.97(PCB 아님) × 0.97(유해화학물질 아님) = 0.677이다.
gain = 3.045 − (0.677 × ln 5 + 0.323 × ln 21) = 3.045 − (0.677 × 1.609 + 0.323 × 3.045) = 0.972.

묶음 질문 하나로 사실 네 개를 확인하고 후보를 21개에서 5개로 줄일 가능성이 가장 크므로 이것을 묻는다. 계산 내역은 매 턴 Trace의 `score_breakdown`에 남는다.

## 6. 분기와 충돌

### 6.1 자동 채움(질문 전에)
평가 뒤 다음 경우는 묻지 않고 값을 채운 뒤(출처 `DERIVED`) 다시 평가한다. 한 턴에 최대 3번.
- 상위 분류에 속한 세부 값이 하나뿐이면 그 값(예: 소재 분류 "혼합물" → 소재 "혼합물").
- `auto_single` 사실 하나만 확정을 막고 있고 선택지가 하나면 그 값(별표 4 번호 후보가 하나).

### 6.2 분기 순서
위에서부터 처음 해당하는 분기를 고른다.

| 순서 | 분기 | 조건 | 건 상태 |
|---|---|---|---|
| 1 | `RESOLVE_CONFLICT` | 충돌이 있거나 후보가 0개(6.4절) | 문진 중 |
| 2 | `UNSUPPORTED` | 적용 테이블 없음·여럿, 같은 우선순위 동률, 질문 상한(기본 12회) 도달, 남은 미확인이 모두 "모름"이거나 서류를 거부함 (모두 결론이 나지 않은 경우만) | 정보 부족 |
| 3 | `ASK_FACT` | 확정 전이고 물을 수 있는 사실이 있음 → 5절로 질문 하나 | 문진 중 |
| 4 | `REQUEST_EVIDENCE` | 서류로만 확인할 수 있는 사실만 남음 → 서류 종류별로 묶어 요청 | 정보 부족 |
| 5 | `FINAL_REVIEW` | 확정할 수 있음. 번호 없는 결론도 포함. 사용자가 확정을 누를 때까지 | 문진 중 |

사용자가 질문을 던졌으면(예: "PCB가 뭐예요?") 분기에 `ANSWER_USER_QUESTION`을 덧붙인다. 판정 상태는 바뀌지 않는다.

### 6.3 서류로 미루기
"모름"이라 답한 사실에 증빙 종류(예: 시험성적서)가 있으면, 같은 증빙으로 확인할 다른 사실은 하나씩 묻지 않고 서류로 한 번에 받는다. 예: 납 용출 농도를 모르면 다른 용출 항목도 같은 성적서에 있으므로 성적서를 요청한다.

### 6.4 충돌
- **말과 서류가 다름:** 같은 키에 진술(CLAIMED)과 서류 값(EVIDENCED)이 다르고, 그 차이가 규칙 조건의 참·거짓을 하나라도 바꿀 때만 충돌이다. 결론에 영향이 없는 차이는 충돌이 아니다. 같은 값을 다시 말하거나 진술을 철회하면 풀린다.
- **후보 0개:** 모든 규칙이 거짓이면 어떤 사실들 때문에 지워졌는지 최소 설명을 만든다(탐욕적 덮개).

## 7. 한 턴의 처리 순서와 AI의 역할

1. **입력 기록:** 사용자 말이나 버튼 답을 대화 기록에 남긴다.
2. **사실로 바꾸기**
   - 버튼(quick reply): AI를 거치지 않고 바로 사실로 바꾼다. 값은 카탈로그 타입에 맞게 검증한다. 묶음의 "모두 해당 없음"은 열린 사실마다 `none_value`, "해당 있음/모름"은 묶음을 펼친다(이후 사실을 하나씩 묻는다).
   - 자유 입력: AI 추출기가 카탈로그의 사실만 JSON으로 뽑는다(`app/agent/extractor.py`). AI로 보내기 전에 식별 정보를 가린다(`docs/llm-data-policy.md`). AI가 꺼져 있으면 직전 질문의 선택지 라벨과 정확히 같은 답만 받는다.
3. **추출 검사(guard):** 통과한 사실만 이력에 들어간다(`app/agent/guard.py`).
   - 카탈로그에 있는 키만. `internal` 사실은 직전 질문의 선택지 안에서만
   - 근거 문장(quote)이 사용자 말에 실제로 있어야 함
   - 숫자는 그 숫자가 근거 문장에 있어야 함(지어낸 숫자 차단)
   - "모름"은 직전 질문의 사실에만
   - 사용자가 말한 분류번호는 말에 실제로 있는 번호만 받는다. 판정에는 쓰지 않고 질문 가중치(5.3절)에만 쓴다
4. **엔진:** 유효 사실 → 평가(4절) → 자동 채움(6.1절) → 충돌(6.4절) → 분기(6.2절) → 질문(5절). AI를 쓰지 않는다.
5. **응답 문장:** AI 응답기가 분기와 질문을 사람 말로 다듬는다(`app/agent/responder.py`). 검사를 통과하지 못하면 정해진 문장(템플릿)을 쓴다.
   - 문장 안 분류번호와 숫자는 엔진 결과에 있는 것만
   - 질문은 한 턴에 하나
6. **상태와 기록:** 질문 분기면 질문 횟수를 하나 올린다. 턴마다 Trace를 남긴다(8절).

AI가 틀려도 결과가 틀리지 않는 이유: AI는 사실을 **제안**만 하고, 그 제안은 3번 검사를 통과해야 하며, 분류번호는 4절 규칙만 정한다. AI가 모두 실패해도 버튼 답만으로 끝까지 진행할 수 있다.

## 8. 확정·다시 열기·기록

- **건 상태:** 문진 중(`DIAGNOSING`, 질문·충돌·확정 검토) ↔ 정보 부족(`NEEDS_INFO`, 서류 요청·판정 불가) → 확정(`CODE_CONFIRMED`) → 운반 중(`IN_TRANSIT`) → 완료(`COMPLETED`). 문진은 앞의 두 상태에서만 받는다. 상태 전이 전체는 `docs/api/api-spec.md` 7절.
- **확정(confirm):** 서버가 지금 사실로 **다시 평가**해서 확정 가능할 때만 받는다. 화면이 본 번호(`expected_code`)와 다르면 거절한다. 확정하면 판정 버전과 인계 객체(`docs/handoff-contract.md`)를 저장하고, 그때까지의 Trace를 고칠 수 없게 잠근다.
- **다시 열기(reopen):** 확정한 건을 다시 문진 상태로 돌린다. 이전 판정 버전은 보존된다.
- **규칙 버전:** 건마다 시작할 때의 규칙 버전(`kb_version`, 규칙 데이터 해시)을 저장한다. 규칙이 바뀐 뒤 쓰기 요청이 오면 `KB_CHANGED`로 막고, `rebase`로 지금 규칙에 맞춰 다시 평가한다(`docs/api/server-engine-contract.md` 3.2절).
- **Trace:** 턴마다 판정을 재현할 수 있는 정보를 남긴다. 입력, 추출 결과, 추가된 사실, 유효 사실, 테이블·버전, 거짓이 아닌 규칙의 평가 결과, 충돌, 분기와 이유, 질문 점수 내역, AI 호출 기록(가린 문장과 해시).

## 10. 처음 설계와 달라진 점

처음 구현 지시서(저장소 밖 문서)에서 다음을 보강했다.
- **blocking_facts:** 지시서는 미확인 사실 전체에서 질문을 골랐다. 지금은 확정을 실제로 막는 사실에서만 고른다(4.5절).
- **gain이 0인 질문 제외와 fallback:** 후보를 줄이지 못하는 질문은 고르지 않고, 모두 0이면 규칙 해소 정도로 고른다(5.3절).
- **묶음 질문과 2단계 소재 질문:** 소재 97개를 한 번에 묻던 첫 질문을 분류 13개 → 소재로 나눴다(`docs/history/material-2step.md`).
- **번호 선택은 마지막(`ask_last`)과 자동 채움(`auto_single`):** 별표 4 번호는 다른 조건이 다 풀린 뒤 묻고, 하나뿐이면 묻지 않는다.
- **번호 없는 결론도 확정:** 폐기물 아님·적용 제외·해석 필요 등도 확정하고 경로추천에 안내를 넘긴다(`docs/handoff-contract.md`).
- **철회와 서류 효력 해제:** 사실 이력을 지우지 않고 표시 행으로 평가에서 뺀다(3.2절).
