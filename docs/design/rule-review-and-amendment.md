# 규칙 검토와 법령 개정 반영 설계

- 상태: **제안**(구현 전). 6절의 결정이 나면 단계별로 구현한다.
- 작성: 2026-11-09
- 관련: [docs/engine/algorithm.md](../engine/algorithm.md)(엔진 알고리즘), `data/real/conversion_report.md`(변환 보고서)

## 0. 요약

**문제:** 비개발자인 도메인 전문가가 다음 두 가지를 할 수 없다.
- 엔진의 규칙이 법령대로 만들어졌는지 검토하기
- 법령이 개정됐을 때 그 부분만 골라 반영하기

**원인:** 엔진이 읽는 규칙은 기존 엔진의 원본 규칙을 소재별로 펼쳐 만든 **생성물**이다(테이블 97개, 규칙 3,534개). 사람이 읽기 좋은 원본은 이 저장소 밖에 있고, 검토 결과를 남길 곳이 없으며, 버전 관리는 규칙 전체 단위다.

**제안:**
1. 원본 규칙(법 규칙 150개, 소재 98개, 번호 대응표)을 이 저장소로 가져와 **유일한 원본**으로 삼는다. 엔진용 테이블은 빌드 결과물로만 둔다.
2. 원본 규칙마다 **사람이 읽는 검토 카드**를 자동으로 만들고, 검토 결과를 **검토 기록 파일**에 남긴다. 규칙 내용이 바뀌면 검토가 자동으로 풀린다.
3. 전문가가 쓰는 **정답 사례표**(CSV)로 엔진을 검증한다. "예전 엔진과 같은가"가 아니라 "전문가 판단과 같은가"를 본다.
4. 법령 개정은 **조문 → 영향받는 규칙**을 뽑는 영향 보고서에서 시작한다. 바뀐 원본 규칙에만 시행일을 붙인 새 판을 추가하고, 판정이 달라지는 사례를 차이 보고서로 확인한 뒤 반영한다.
5. 규칙 버전을 **테이블 단위**로 비교해, 개정과 관계없는 진행 중인 건은 막지 않는다.

## 1. 지금 구조와 문제

```
 [저장소 밖] 기존 엔진 resource_engine/rules/          [이 저장소] data/real/
 ┌────────────────────────────────────┐   변환기     ┌──────────────────────────────┐
 │ 법 규칙 150개 (rules.yaml 28 +       │ ───────────▶ │ 소재별 테이블 97개             │──▶ 엔진
 │   rules_s3.yaml 122)                │ convert_     │ 규칙 3,534개                  │
 │ 소재 98개 (materials.yaml)          │ legacy.py    │ (법 규칙 × 소재 × 번호 선택)    │
 │ 번호 대응표 (s4_map.yaml)            │              │ review: 모두 UNVERIFIED       │
 │ 별표 4 번호 376개, 근거 문서 14개     │              └──────────────────────────────┘
 └────────────────────────────────────┘
```

측정한 사실(2026-11-09):

| 항목 | 값 | 의미 |
|---|---|---|
| 원본 법 규칙 | 150개, 모두 `plain`(쉬운 설명)·`quote`(인용문)·`location`(조문 위치) 있음 | 원본은 이미 사람이 읽기 좋다 |
| 원본이 가리키는 조문 | 서로 다른 (근거 문서, 조문 위치) 61개 | 조문 단위 추적이 가능한 재료가 있다 |
| 원본 1개 → 생성 규칙 | 중앙값 5개, **최대 870개** | 생성물을 직접 고치면 수백 곳을 고쳐야 한다 |
| 기름 5% 규칙 | 원본 1개 → 생성 테이블 87개에 복사 | 같은 기준이 87곳에 있다 |
| 생성 규칙의 근거 ID | 7종(`DEC-A1` 2,376회, `RULE-A4` 1,861회) | 조문 위치는 설명 글(`ref`)에만 남아 검색이 어렵다 |
| 검토 상태 | 원본 150개, 생성 규칙 모두 `UNVERIFIED` | 검토를 기록하는 절차가 없다 |
| 시행일 | 97개 테이블 모두 `2026-10-02` 하나 | 엔진은 시행 기간을 지원하지만 쓰이지 않는다 |
| 규칙 버전 | 규칙 데이터 **전체**의 해시(`kb_version`) | 테이블 하나만 고쳐도 모든 진행 중인 건이 `KB_CHANGED` |
| 검증 기준 | 기존 엔진 판정표 4,281행과 비교 | 기존 엔진이 틀렸다면 함께 틀린 채로 통과 |
| 원본 위치 | 다른 저장소의 작업 브랜치(`2f1355a`) | develop → main 릴리스 때 기존 엔진 파일이 사라진다 |

## 2. 목표와 범위

**목표**
- 전문가가 개발 도구 없이 규칙을 읽고, 검토하고, 결과를 남길 수 있다.
- 법령 개정 시 영향받는 규칙을 바로 찾고, 그 부분만 바꾸고, 바뀌는 판정을 미리 본다.
- 개정과 관계없는 진행 중인 건은 영향을 받지 않는다.

**바꾸지 않는 것**
- 엔진의 평가·질문 선택 알고리즘([algorithm.md](../engine/algorithm.md) 4~6절)과 엔진용 테이블 형식
- API 필드. `review` 값이 실제 검토 상태를 반영하게 되는 것과, `KB_CHANGED`의 `details`에 필드가 추가되는 것만 달라진다

**범위 밖**
- 기존 엔진의 R코드(S5)·결정 카드 기능
- 규칙을 화면에서 직접 고치는 편집기(6절 결정 2에 따라 나중에)

## 3. 설계

### 3.1 원본 규칙을 이 저장소의 유일한 원본으로

```
 knowledge/                     ← 전문가가 보는 곳(원본)
 ├─ sources.yaml                근거 문서: 법령명, 법령 번호, 시행일
 ├─ law_rules/*.yaml            법 규칙(범위·사업장·지정폐기물 기준). 쉬운 설명·인용문·조문 위치
 ├─ materials.yaml              소재: 폐기물 종류, 소재가 정하는 사실, 번호 후보 (법 판단 없음)
 ├─ code_map.yaml               법 규칙 → 별표 4 번호 범위 대응
 ├─ annex4_codes.yaml           별표 4 번호표
 ├─ facts.yaml                  사실 정의 + 지금 legacy_overrides.yaml의 보정값
 ├─ reviews.yaml                검토 기록(3.3절)
 └─ expert_cases.csv            정답 사례표(3.4절)
            │  uv run python tools/build_kb.py
            ▼
 data/real/                     ← 엔진이 읽는 곳(생성물, 직접 고치지 않음)
 └─ ... 지금과 같은 형식 + 생성 규칙마다 origin(원본 규칙 ID)·조문 위치
```

- 기존 엔진 `rules/`의 해당 파일을 `knowledge/`로 옮긴다. 기존 엔진 원본 이력은 저장소 이력(main의 부모)에 남는다.
- `tools/convert_legacy.py`를 `tools/build_kb.py`로 바꾼다. 외부 경로(`LEGACY_ENGINE_DIR`) 대신 `knowledge/`를 읽는다. 변환 로직(우선순위 대역, 소재별 펼치기)은 그대로 쓴다.
- 생성 규칙에 다음 필드를 더한다. 로더는 모르는 필드를 무시하도록 확인한다.
  - `origin`: 원본 규칙 ID(예: `S3-6-OIL-5PCT`)
  - `basis[].location`: 조문 위치(예: `별표 1 제6호`)
- **CI 검사 추가:** `build_kb.py --check`가 "지금 `data/real/`이 `knowledge/`로 만든 결과와 같은가"를 확인한다. OpenAPI 최신 검사와 같은 방식이다. 생성물을 손으로 고치면 CI가 실패한다.

### 3.2 조문 단위 근거와 색인
- 원본 규칙의 `source`(문서) + `location`(조·항·호·목)을 조문 키로 쓴다. 예: `DEC-A1 별표 1 제6호`.
- 빌드할 때 **색인**(`data/real/index.json`)을 만든다: 조문 키 → 원본 규칙 → 생성 규칙·테이블. 3.5절 영향 보고서와 검토 카드가 이 색인을 쓴다.
- `location` 표기는 정해진 형식으로 맞춘다(예: `별표 1 제6호`, `제2조 제1호`). 빌드가 형식을 검사한다.

### 3.3 전문가 검토

**검토 카드(자동 생성).** `tools/build_kb.py --review-pages`가 원본 규칙마다 한 장씩 만든다. 형식은 HTML 한 묶음(브라우저로 열기)이고, 같은 내용을 CSV로도 낸다. 아래는 실제 원본 규칙 `S3-6-OIL-5PCT`로 그린 모양 예시다(N은 빌드가 계산).

```
 ┌ S3-6-OIL-5PCT ─────────────────────────────── 검토 전 ┐
 │ 폐유(기름성분 5% 이상 함유)                               │
 │ 쉬운 설명: 기름이 묻거나 섞인 폐기물도 기름성분이 5% 이상이면   │
 │           폐유(지정폐기물)로 봅니다. 함량은 시험으로 확인합니다.│
 │ 조건: 폐기물 종류가 [폐유·폐식용유·흡착제]가 아니고            │
 │       그리고 기름 여부 = 묻어 있거나 섞여 있음                 │
 │       그리고 기름 함량 ≥ 5% (시험성적서로 확인해야 함)          │
 │ 결론: 지정폐기물 → 별표 4 06 그룹(폐유)                      │
 │ 근거: 폐기물관리법 시행령 별표 1 제6호                        │
 │       "폐유[기름성분을 5퍼센트 이상 함유한 것을 포함하며 …]"     │
 │ 적용 소재: 87개 (PP, PE, …)   이 규칙으로 정해지는 판정: N행    │
 │ [맞음] [고쳐야 함] [틀림]  의견: ______                      │
 └──────────────────────────────────────────────────────┘
```

- 조건은 사실 카탈로그의 라벨로 문장으로 바꿔 쓴다. 개발용 키(`oil_content_pct`)는 보이지 않는다.
- 카드 순서는 영향이 큰 것부터다(적용 소재 수, 이 규칙으로 정해지는 회귀 행 수).
- 소재 카드도 만든다. 소재는 법 판단을 하지 않고 "폐기물 종류, 소재가 정하는 사실, 번호 후보"만 정한다는 점을 카드에 적는다.

**검토 기록(`knowledge/reviews.yaml`).**

```yaml
- rule: S3-6-OIL-5PCT
  content_hash: 3f9a…          # 검토할 때의 원본 규칙 내용 해시
  status: VERIFIED             # VERIFIED | NEEDS_CHANGE | REJECTED
  reviewer: 홍길동(○○협회)
  reviewed_at: 2026-11-20
  comment: 시행령 문언과 일치
```

- 원본 규칙 내용이 바뀌면 해시가 달라져 **자동으로 "검토 전"**이 된다. 개정 반영 뒤 다시 검토해야 한다.
- 빌드는 생성 규칙의 `review`에 원본 규칙의 검토 상태를 넣는다. 인계 객체 `review`와 화면의 "검토 전 규칙 · 참고용" 표시가 실제 상태를 따라간다.
- 결론 하나에 여러 원본 규칙이 관여하면(예: 지정폐기물 규칙 + 번호 대응표) 모두 검토된 경우에만 `VERIFIED`로 낸다.

**처음에는 전문가가 파일을 직접 고치지 않는다(6절 결정 2).** 카드에서 고른 결과를 CSV나 양식으로 받고, 개발자가 `reviews.yaml`에 옮긴다.

### 3.4 정답 사례표

전문가가 "이런 폐기물이면 이 결론"을 표로 쓴다. 엑셀로 쓰고 CSV로 저장한다. 아래 두 행은 형식 예시다.

| id | 상황 | 사실 | 기대 결론 | 근거 | 작성자 |
|---|---|---|---|---|---|
| E001 | PP 사출 스크랩, 오염 없음 | 소재=PP(폴리프로필렌); 배출 시 상태=고체; 기름·잔류물·PCB·유해화학물질=모두 해당 없음; 배출시설 허가·신고=예 | 51-03-01 | 시행규칙 별표 4 | 홍길동 |
| E002 | 절삭유가 묻은 철 스크랩, 기름 7% | 소재=고철(철 스크랩); 기름=기름이 묻어 있거나 섞여 있음; 기름성분 함량=7 (성적서) | 06 그룹 | 시행령 별표 1 제6호 | 홍길동 |

- **사실 열은 화면 라벨로 쓴다**(소재=PP(폴리프로필렌)). 묶음 질문은 묶음 이름=모두 해당 없음으로 쓴다. 실행기가 카탈로그의 라벨을 키·값으로 바꾼다. 못 바꾸면 그 행에 이유를 적어 돌려준다. 값 뒤 `(성적서)`는 서류로 확인한 값(EVIDENCED)이라는 뜻이다.
- 기대 결론은 분류번호, 번호 그룹(앞자리), 또는 결론 종류(폐기물 아님, 해석 필요 등)다.
- `scripts/expert_cases.py`가 엔진을 돌려 **쉬운 보고서**를 만든다: 맞음 / 다름 / 판정 못함, 그리고 다를 때 어떤 원본 규칙이 성립했는지. CI에서 돌리고, "다름"은 이슈로 남긴다(처음에는 실패로 막지 않음).
- 기존 엔진과의 회귀 비교(`tools/legacy_regression.py`)는 "의도하지 않은 변화"를 잡는 용도로 유지한다. 정답 기준은 정답 사례표다.

### 3.5 법령 개정 반영 흐름

| 단계 | 하는 일 | 누가 | 도구 |
|---|---|---|---|
| 1. 접수 | 개정 법령을 `knowledge/sources.yaml`에 새 판으로 추가(법령 번호, 공포일, 시행일) | 전문가 → 개발자 | - |
| 2. 영향 보고 | 바뀐 조문을 넣으면 영향받는 원본 규칙, 생성 규칙 수, 소재, 회귀 행, 정답 사례, 진행 중인 건 수를 뽑는다 | 개발자가 실행, 전문가가 읽음 | `tools/impact.py --source DEC-A1 --location "별표 1 제6호"` |
| 3. 변경 요청 | 원본 규칙별로 새 조건·인용문·시행일과 "바뀌어야 할 판정 사례"를 적는다 | 전문가 | 이슈 양식 "규칙 변경 요청" |
| 4. 새 판 추가 | 바뀐 원본 규칙에만 **새 판**을 추가한다(`effective_from` = 시행일). 이전 판에는 `effective_to`를 단다. 이전 판은 지우지 않는다 | 개발자 | 원본 파일 |
| 5. 빌드·차이 보고 | 원본 규칙의 차이를 문장으로, 판정이 달라지는 회귀 행·정답 사례를 표로 낸다 | 자동 | `build_kb.py --diff develop` |
| 6. 확인 | 차이 보고서를 보고 승인하고, 바뀐 규칙을 다시 검토한다(3.3절) | 전문가 | 검토 카드 |
| 7. 반영 | PR → CI(생성물 최신, 정답 사례, 회귀 기준 갱신) → develop | 개발자 | - |

**시행일 처리.** 엔진은 이미 규칙마다 시행 기간을 두고, 건마다 법 기준일(`as_of`)에 유효한 판만 쓴다([algorithm.md](../engine/algorithm.md) 2.3절). 지금은 빌드가 원본 규칙의 날짜를 생성 규칙으로 넘기지 않는다. 빌드가 원본 규칙의 `effective_from`·`effective_to`를 생성 규칙에 그대로 옮기도록 바꾼다. 그러면 개정 전에 시작한 건과 후에 시작한 건이 각자 맞는 판으로 평가된다.

**규칙 변경 요청 양식(이슈 템플릿).** 원본 규칙 ID(또는 "새 규칙"), 바뀐 조문과 새 문언, 시행일, 바뀌어야 할 판정 사례(정답 사례표 형식), 경과 조치 여부.

### 3.6 규칙 버전을 테이블 단위로

지금은 규칙 데이터 전체의 해시 하나(`kb_version`)를 세션에 저장하고, 다르면 쓰기 요청을 `KB_CHANGED`로 막는다. 바꿀 내용:
- 테이블 버전을 내용 해시로 만든다. 해시에 넣는 것: 그 테이블의 규칙, 포함한 공통 규칙, 쓰는 사실 정의.
  - 지금은 모든 테이블 버전이 `2026.11.0+re-<기존 엔진 커밋>`으로 같다.
- 세션에는 이미 `table_versions`가 저장된다. 비교 기준을 다음으로 바꾼다.
  - 적용 테이블이 정해진 건: **그 테이블의 버전**이 같으면 계속 진행한다.
  - 아직 테이블이 정해지지 않은 건(소재 모름): 테이블 선택 조건과 사실 정의가 같으면 계속 진행한다.
- 전체 해시(`kb_version`)는 재현용으로 계속 기록한다. `KB_CHANGED`의 `details`에 `changed_tables`를 더한다(필드 추가만).

## 4. 단계별 작업

| 단계 | 내용 | 규모(추정) | 끝나면 할 수 있는 것 |
|---|---|---|---|
| P1 | 원본을 `knowledge/`로 이관, `build_kb.py`, 생성물 최신 CI 검사, 생성 규칙에 `origin`·`location` | 1~1.5일 | 저장소 밖 의존 없이 빌드. 생성물을 손으로 고치는 실수 방지 |
| P2 | 검토 카드(HTML·CSV), `reviews.yaml`, 검토 상태를 생성 규칙·인계 객체에 반영 | 1.5~2일 | 전문가가 규칙을 읽고 검토 결과를 남김 |
| P3 | 정답 사례표 형식, 실행기와 쉬운 보고서, CI | 1일 (+ 전문가 작성 시간) | 전문가 판단 기준 검증 |
| P4 | 조문 색인, 영향 보고서, 차이 보고서, 시행일 판 처리, 변경 요청 양식 | 1.5~2일 | 개정 반영 흐름 전체 |
| P5 | 테이블 단위 버전 비교 | 0.5~1일 | 개정과 무관한 진행 중인 건이 막히지 않음 |
| P6 | (선택) 전문가가 직접 고치는 스프레드시트 입력 또는 편집 화면 | 결정 후 | 개발자 없이 변경 |

- 순서는 P1 → P2 → P3이 먼저다. P4·P5는 P1이 끝나면 따로 진행할 수 있다.
- 각 단계는 별도 PR로 develop에 넣는다.
- 규모는 지금 코드를 기준으로 한 추정이고, 원본 파일 정리에 따라 달라질 수 있다.

## 5. 검토한 다른 방법

| 방법 | 장점 | 택하지 않은 이유 |
|---|---|---|
| 생성 테이블(3,534개)을 직접 원본으로 쓰기 | 빌드 단계가 없다 | 원본 1개가 최대 870곳에 복사돼 있어 검토·개정이 불가능하다 |
| 엔진이 원본 규칙을 직접 평가(빌드 없음) | 생성물이 없다 | 평가기·질문 선택기·회귀 검증 자산을 다시 만들어야 한다. 효과는 빌드 방식과 같다 |
| 규칙 원본을 별도 저장소에 두기 | 규칙 변경 권한을 코드와 분리 | 빌드·CI·버전이 두 저장소에 걸친다. 지금 팀 규모에서는 관리 부담이 크다(6절 결정 1) |
| 처음부터 규칙 편집 화면 만들기 | 전문가가 직접 고침 | 검토 카드·정답 사례로 먼저 쓰임새를 확인한 뒤 정하는 편이 낫다 |

## 6. 정해야 할 것

| # | 결정 | 제안 |
|---|---|---|
| 1 | 규칙 원본을 어디에 둘까 | 이 저장소 `knowledge/`(엔진과 함께 버전 관리) |
| 2 | 전문가가 파일을 직접 고칠까 | 처음에는 검토 카드·변경 요청 양식으로 받고 개발자가 반영. 쓰임새를 본 뒤 P6 결정 |
| 3 | 누가 검토자가 될 수 있나, 한 명이면 충분한가 | 전문가 팀이 정함. `reviews.yaml`은 여러 명 기록을 지원 |
| 4 | 개정 시행 전후 건은 어느 판으로 판정하나 | 지금은 대화를 시작한 날(`as_of`) 기준이고, 다시 열어도 바꾸지 않는다. 법적으로 맞는지 전문가 확인 필요(예: 배출일 기준이어야 하는지) |
| 5 | 검토되지 않은 규칙의 결과를 어떻게 보여 줄까 | 지금처럼 "검토 전 규칙 · 참고용" 유지. 모두 검토된 판정만 표시를 뗀다 |
| 6 | 법령 원문 파일(PDF)을 저장소에 둘까 | 기존 엔진의 원문 113MB는 git에 없다(로컬만). 저장소에는 출처·법령 번호·인용문만 두고, 원문은 별도 저장소(공유 드라이브 등)에 둔다 |
| 7 | 정답 사례의 "다름"을 CI 실패로 막을까 | 처음에는 보고만 하고, 사례표가 안정되면 실패로 바꾼다 |
